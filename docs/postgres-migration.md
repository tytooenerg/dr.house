# Caminho de migração SQLite → Postgres

Este documento é deliberadamente honesto sobre escopo: **a migração não está implementada
neste repositório** — o que existe é o caminho real para fazer, mapeado contra o código
atual, para que a decisão (quando e como migrar) seja informada em vez de adivinhada.
SQLite (`better-sqlite3`, ver `server/src/db/index.ts`) é uma escolha real e defensável até
um certo ponto de escala — é rápido, zero-config, e todo o resto deste projeto (WAL mode,
backups automáticos, migrations versionadas) já assume esse ponto de partida. Não é preciso
migrar antes de precisar.

**Atualização — o schema em si foi de fato traduzido e validado contra um Postgres 16 real**
(não apenas revisado à mão): `scripts/postgres/generate-schema.mjs` traduz as 53 migrations
SQLite para `server/src/db/migrations-postgres/*.sql`, e `scripts/postgres/validate-schema.sh`
aplica todas elas, em ordem, contra um banco Postgres 16 real e descartável via `psql`. As
53 migrations aplicam sem erro e produzem as 68 tabelas esperadas; um smoke test seguinte
(inserir um `user`, inserir uma `duplicata` referenciando-o, fazer o join de volta) confirmou
que as foreign keys e as cinco migrations que precisaram de tradução manual (não só regex)
funcionam corretamente juntas, não só que o DDL "parseia". Ver `scripts/postgres/README.md`
para o que exatamente foi traduzido, dois problemas reais descobertos rodando contra um
Postgres de verdade (não hipotéticos) e o que isso **não** prova — a tradução cobre só o
schema; a camada de queries em runtime (driver síncrono → assíncrono, todo `server/src/db/`)
continua sendo o trabalho real e não iniciado descrito abaixo.

## Quando migrar de verdade

Sinais concretos de que chegou a hora, não uma data no calendário:

- Mais de uma instância da API precisando escrever no mesmo banco (SQLite com WAL suporta
  múltiplos leitores + um escritor; múltiplos processos escrevendo concorrentemente é onde
  ele para de ser a ferramenta certa).
- Tamanho do arquivo `.db` ficando grande o bastante para que backup/restore (hoje via
  cópia de arquivo, `server/src/lib/backup.ts`) comece a demorar de forma perceptível.
- Necessidade real de réplica de leitura geograficamente distribuída.

Nenhum desses é hoje uma limitação real deste protótipo — são o motivo de isto ser um
documento, não uma migration já escrita.

## O que precisa mudar no código

1. **Driver**: trocar `better-sqlite3` (síncrono) por um driver assíncrono para Postgres
   (`pg` ou `postgres`). Isso é a mudança mais invasiva — todo `db/*.ts` neste repositório
   usa `db.prepare(...).get()/.all()/.run()` de forma síncrona; a versão Postgres exige
   `await` em cada chamada. Não há atalho: cada uma das ~30 arquivos em `server/src/db/`
   precisa ser revisitada.
2. **SQL não-portável nas migrations — já traduzido e validado**, não mais uma lista
   hipotética: `scripts/postgres/generate-schema.mjs` faz essa tradução de verdade e
   `server/src/db/migrations-postgres/` é o resultado real, aplicado com sucesso contra um
   Postgres 16. As únicas duas substituições mecânicas necessárias em 53 migrations foram
   `AUTOINCREMENT` → `GENERATED BY DEFAULT AS IDENTITY` (não `GENERATED ALWAYS` — algumas
   migrations reconstroem uma tabela preservando os `id`s originais, o que `ALWAYS`
   rejeita; descoberto rodando contra Postgres de verdade, não hipotetizado) e
   `datetime('now')` → `now()`. Cinco migrations (`0004`, `0006`, `0049`, `0050`, `0053`)
   precisaram de tradução manual real, não regex: todas usam o único jeito do SQLite de alargar um `CHECK`
   (reconstruir a tabela inteira) — em Postgres isso é só `ALTER TABLE ... DROP/ADD
   CONSTRAINT`, sem reconstrução nenhuma. Detalhes completos e os dois erros reais
   encontrados no processo em `scripts/postgres/README.md`.
   Ainda **não coberto** por essa tradução (porque não aparece em nenhuma migration, só em
   queries em runtime dentro de `server/src/db/*.ts` e `server/src/lib/*.ts`): variantes
   como `datetime('now', '-N hours')` (viraria `now() - interval 'N hours'` em Postgres) e
   `strftime(...)`. Buscar por essas duas strings fora do diretório de migrations dá a
   lista exata de pontos a revisar quando a camada de queries for de fato portada.
3. **Migrations**: o runner atual (`server/src/db/migrate.ts`) é simples o bastante (lê
   `.sql` do diretório, aplica em ordem, registra em `schema_migrations`) para continuar
   funcionando com syntax Postgres nos arquivos — o mecanismo de versionamento não precisa
   mudar, só o SQL dentro de cada migration, que já existe traduzido em
   `server/src/db/migrations-postgres/`.
4. **`:memory:` nos testes**: a suíte de testes (`server/test/setup.ts`) usa
   `DB_PATH=':memory:'` para isolar cada arquivo de teste com um banco limpo e rápido.
   Postgres não tem equivalente direto — a alternativa real é um schema Postgres novo (ou
   um container Postgres efêmero) por execução de teste, o que torna a suíte
   consideravelmente mais lenta a não ser que se invista em paralelização real.
5. **`journal_mode = WAL` e `foreign_keys = ON`**: esses dois `db.pragma(...)` em
   `db/index.ts` são específicos do SQLite — não têm equivalente 1:1 (Postgres já impõe FK
   por padrão; WAL não se aplica).

## O que **não** precisa mudar

- O modelo de dados em si (tabelas, colunas, relacionamentos) é portável quase 1:1 — **agora
  verificado**, não só assumido: as 53 migrations traduzidas aplicam sem erro contra um
  Postgres 16 real e um smoke test confirmou que os relacionamentos (foreign keys) e os
  `CHECK` constraints continuam funcionando exatamente como no SQLite (`scripts/postgres/`).
- Toda a lógica de negócio fora de `server/src/db/` (routes, lib) não sabe qual banco está
  por trás — ela só chama funções de `db/*.ts`. Migrar bem o driver e reescrever os
  arquivos de `db/` de forma síncrona→assíncrona propaga automaticamente para o resto do
  app, desde que cada `await` seja adicionado corretamente nas camadas acima (routes já são
  `async` na maioria dos casos, então o impacto ali é menor do que parece).
- `lib/cache.ts` (cache opcional Redis/memória) e o relay de WebSocket via Redis
  (`server/src/ws.ts`) já são independentes do banco — nada muda ali.

## Recomendação prática

Não migrar preventivamente. Quando um dos sinais de "quando migrar" acima aparecer de
verdade, o trabalho restante é: (1) escrever um adaptador `db/index.ts` alternativo atrás
da mesma interface síncrona hoje usada — ou aceitar o custo de tornar tudo assíncrono de
uma vez —, (2) ~~portar as ~30 migrations SQL~~ **já feito e validado**
(`server/src/db/migrations-postgres/`, ver acima), (3) portar as poucas variantes de
`datetime`/`strftime` que sobram na camada de queries em runtime (não nas migrations — lista
exata no item 2 acima), (4) trocar o `:memory:` dos testes por um schema descartável.
Esforço real de dias, não de horas, mas menor do que antes desta verificação e bem contido
pelo fato de a lógica de negócio nunca ter acoplamento direto com SQLite fora da camada
`db/`.
