# Postgres schema translation + validation

Two scripts that turn the honest-but-previously-unverified claim in `../../docs/postgres-migration.md` ("the data model is portable almost 1:1") into something actually checked against a real Postgres server, not just read and agreed with.

```bash
# 1. Translate server/src/db/migrations/*.sql (SQLite) → server/src/db/migrations-postgres/*.sql (Postgres)
node scripts/postgres/generate-schema.mjs

# 2. Apply every translated migration, in order, to a real throwaway Postgres database
#    (creates it, applies, prints \dt, drops it — needs a reachable Postgres; PGHOST/PGPORT/PGUSER env vars, defaults assume a local trust-auth instance)
bash scripts/postgres/validate-schema.sh
```

Both were actually run against a real local PostgreSQL 16 (`apt install postgresql-16`, `pg_ctlcluster 16 main start`) while building this — not hand-reviewed and assumed to work. All 38 migrations apply cleanly and produce all 58 tables; a follow-up smoke test (insert a user, insert a duplicata referencing it, join them back) confirmed the foreign keys and the two hand-translated CHECK-widening migrations (see below) work correctly together, not just parse.

## What `generate-schema.mjs` actually does

A narrow, mechanical translation — a grep across all 38 SQLite migrations turned up exactly two non-portable patterns:

- `INTEGER PRIMARY KEY AUTOINCREMENT` → `INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` (not `GENERATED ALWAYS` — several migrations rebuild a table by copying rows with their *original* id values across, which `GENERATED ALWAYS` rejects; this was discovered by the validation script actually failing with `ERROR: cannot insert a non-DEFAULT value into column "id"` on the first attempt, not assumed upfront).
- `datetime('now')` → `now()`.

Two migrations (`0004_admin_kyb_status.sql`, `0006_partner_network.sql`) needed real hand-translation, not a regex: both use SQLite's only way to widen a `CHECK` constraint (SQLite can't `ALTER` one) — rebuild the whole table, copy every row across, drop the original, rename the copy into place. Applying that rebuild's `DROP TABLE users` against Postgres fails for a real reason: Postgres tracks foreign keys as catalog constraints and refuses to drop a table ten others still reference (`cannot drop table users because other objects depend on it`) — SQLite doesn't track FK dependents that way, so the identical statement silently succeeds there. The honest fix is that Postgres never needed the rebuild idiom: `ALTER TABLE ... DROP/ADD CONSTRAINT` changes a CHECK directly, no table copy, no dropped-then-restored FK linkage. The resulting Postgres migration is simpler than the SQLite one it replaces — see `REBUILD_OVERRIDES` in `generate-schema.mjs` for the exact statements and how the constraint name (`users_role_check`) was confirmed rather than guessed.

## What this does *not* prove

This validates the **schema only** — that the DDL is valid Postgres and preserves the same tables, columns, constraints and referential integrity. It does not touch (and `docs/postgres-migration.md` is still honest that these remain real, unstarted work):

- The driver (`better-sqlite3`, synchronous) → an async Postgres driver (`pg`), which means every one of the ~30 `server/src/db/*.ts` files needs its calls rewritten to `await`.
- The runtime query layer's own SQLite-specific syntax outside migration files (`strftime`, more `datetime('now', ...)` variants) used in `lib`/`db` query strings, not just DDL.
- Wiring `migrations-postgres/` into `server/src/db/migrate.ts`'s runner as an actual alternate driver path.
- Making `server/test/setup.ts`'s per-test-file `:memory:` isolation work against Postgres (no direct equivalent — needs a disposable schema or container per test file).
