# Lastro — Plataforma de Duplicatas Escriturais

Marketplace/infraestrutura de duplicatas escriturais que conecta **Empresa Cedente** (emite e antecipa recebíveis), **Empresa Sacado** (confirma/contesta dívidas), **Investidor/Financiador** (bancos, FIDCs, fundos, securitizadoras, factorings) e **Seguradora parceira** (apólices e sinistros) numa única infraestrutura — com registro escritural (CERC/B3/Núclea), score de risco por IA, seguro sobre o recebível, central de compliance com trilha de auditoria, e uma API pública versionada (`/api/v1`) para integrações de parceiros.

This repo is a full-stack recreation of the original high-fidelity HTML/JS design handoff (`design_handoff_lastro/`), rebuilt as a real, multi-tenant React + TypeScript SPA backed by an Express + SQLite API — with production-grade security, observability, an admin back-office, and a three-tier test suite (unit, component, E2E).

## Stack

- **client/** — React 18 + TypeScript + Vite + React Router + Tailwind CSS
- **server/** — Express + TypeScript + SQLite (better-sqlite3), JWT auth with refresh-token rotation, Zod validation, a WebSocket feed for live auction updates, and a Vitest/Supertest test suite
- **e2e/** — Playwright end-to-end tests running against a production build of the whole app

The client talks to the server exclusively over `/api/*` (proxied by Vite in dev, same-origin in production) plus a `/ws/market` WebSocket for live marketplace updates. There is no client-only mocked state — every action (register, buy an offer, emit a duplicata, resolve a dispute, toggle automation…) is a real HTTP round-trip against a real database, scoped to the authenticated account.

### Highlights

- **Real multi-tenant auth** — bcrypt-hashed passwords, short-lived (15min) JWT access tokens with rotating, single-use refresh tokens (`/api/auth/refresh`), self-service registration per role (investidor/cedente/sacado). Four demo accounts are seeded on first boot (see below).
- **SQLite persistence with versioned migrations** — `server/src/db/migrations/*.sql` + a `schema_migrations` table applied on boot (`npm run db:migrate` also runs them standalone); no more ad-hoc `CREATE TABLE IF NOT EXISTS`.
- **Security hardening** — `helmet`, a CORS allowlist scoped to `/api` (`CORS_ORIGINS`), rate limiting on login/register, and a tamper-evident **audit log** (`audit_log` table, SHA-256 hash chain — each event's hash covers the previous one, so any edited/deleted row breaks the chain from that point forward; verified via `/api/admin/audit`).
- **Admin / back-office role** — a fourth role (`admin`) with its own screen: a KYB approval queue (approve/reject institutional investors, with a reason on rejection), dispute arbitration (decide for cedente or sacado), a Fila de Compliance (duplicatas the Compliance AI Engine suspended for review — see "Claude-assisted features" below), a Uso de IA panel (real per-feature Claude call/token/cost metering — see "Platform hardening" below), and a Jurídico panel (AI-drafted collection/legal documents — see "Legal AI" below). Investors can't bid until their KYB is approved.
- **Live marketplace via WebSocket** — `/ws/market` pushes offer/bid/countdown updates every 2s. Optionally backed by Redis pub/sub (`REDIS_URL`) so the feed fans out correctly if you run more than one API process; a single process works fine without it.
- **Real file uploads** — NF-e attachment (with real Claude-based field extraction — see "Claude-assisted features" below), contract analysis, and KYB regulatory documents go through a real `multipart/form-data` endpoint (`multer`), stored on disk and tracked in the `uploads` table.
- **Real notification emails** — `nodemailer`-backed, respecting each user's notification preferences; logs the email instead of sending when `SMTP_HOST` isn't set, so it works out of the box.
- **CSV/PDF export** — `/api/historico/export.csv` and `.../export.pdf` (via `pdfkit`) for Carteira & Histórico.
- **Real transactional platform fee** (`lib/settlement.ts`) — the tiered take rate shown in the Emitir preview (0,35% up to R$200k, 0,30% up to R$1M, 0,25% above that) is the *same function* actually applied at liquidação: every marketplace/cesta purchase debits the investor's ledger for the full amount and credits the cedente's ledger net of the fee; every mercado secundário resale does the same between the two investors. Real revenue collected to date is shown live in Modelo de Receita (`/app/receita`), computed from every settled purchase — distinct from the illustrative 12-stream revenue mix chart on the same page, which is still a static projected roadmap.
- **Real insurance commission** — contracting insurance on a position (`POST /api/market/:id/insure`, investidor-only) now actually charges the insurer's real premium (INSURERS.premioPct — 0,55%/0,60%/0,68% depending on the seguradora) to the investor's ledger, and pays the registered seguradora account net of Lastro's 18% distribution commission (`INSURANCE_COMMISSION_PCT` in `lib/settlement.ts`). Every settlement is logged to `insurance_settlements` for exact, auditable revenue reporting on Modelo de Receita — switching to a different insurer charges again, but resubmitting the same one or removing insurance doesn't charge or refund (a deliberate simplification, not a proration engine).
- **Real subscription billing** — three plans (Básico/Pro/Empresarial) backed by Stripe Checkout, the Stripe customer portal, and signature-verified webhooks (`/api/billing/webhook`). Automação de Lances requires Pro (Comparador de Taxas is free on every plan, including Básico); live API keys and webhooks require Empresarial (sandbox keys are free on any plan — see Partner API maturity below); a Básico cedente is capped at 5 emissões/mês (+1 per successful referral — see Growth below). Without `STRIPE_SECRET_KEY` set, plan changes are simulated instantly (no real charge) so the whole paywall is demoable out of the box.
- **Seguradora role** — a fifth account type for insurance partners (linked to one of the three seeded insurers). Its dashboard lists every duplicata it's underwritten (with premium totals) and surfaces **sinistros**: duplicatas that went overdue unsold, which the seguradora approves (indenizes the cedente) or denies, all logged to the audit trail.
- **Public partner API (`/api/v1`)** — a versioned, API-key-authenticated surface distinct from the internal SPA API, covering every role that needs to integrate programmatically:
  - Cedente: `POST /duplicatas` (emitir), `GET /duplicatas/:id`.
  - Marketplace: `GET /marketplace`.
  - Sacado: `GET /aceites`, `POST /aceites/:id/status` (confirmar/contestar) — same ownership rules as the SPA's Portal do Sacado.
  - Seguradora: `GET /seguradora` (apólices + sinistros), `POST /seguradora/sinistro/:duplicataId/decidir` — same claims workflow as the Painel da Seguradora.
  - Score: `GET /sacados/:cnpj/score` — real-time credit score/rating lookup by CNPJ, for partners deciding whether to buy a receivable before it's listed.

  Each of these shares its business logic (validation, side effects, notifications, audit logging) with the corresponding internal SPA route via a `lib/*Core.ts` module, so the public API and the app are never allowed to drift out of sync. Keys are generated/revoked from the Desenvolvedores screen (shown once, stored only as a SHA-256 hash), rate-limited per key (`API_RATE_LIMIT_PER_MIN`, default 60/min), and CORS-open (unlike the SPA's strict origin allowlist) since partners call it from their own domains.
- **Partner API maturity** — the kind of things a real integration actually needs, not just the endpoints:
  - **OpenAPI spec** — `GET /api/v1/openapi.json` (public, unauthenticated) documents every partner endpoint; linked from the Desenvolvedores screen so partners can point Swagger/Postman/codegen at it directly.
  - **Sandbox key mode** — keys are generated as `lastro_live_…` or `lastro_test_…` (chosen at generation time); emissions made with a test-mode key are tagged `"mode": "test"` in the response so a partner's integration tests can assert they're not touching production.
  - **Key scopes** — `read_only` vs `read_write` at generation time; a `read_only` key can call every `GET` but is 403'd on every mutating endpoint (`requireWriteScope`), so a partner can hand out a reporting-only key without risking a stray write.
  - **Idempotency-Key** — any mutating `/api/v1` endpoint (`POST /duplicatas`, `POST /aceites/:id/status`, `POST /seguradora/sinistro/:id/decidir`) accepts an `Idempotency-Key` header; replaying the same key + body returns the original response instead of double-emitting/double-deciding, and replaying it with a different body is a `409`. Same contract Stripe uses.
  - **Usage metering** — every authenticated call increments a per-key monthly counter (`api_key_usage`), surfaced per key in Desenvolvedores — the foundation for usage-based billing down the line.
  - **Tiered rate limits** (`auth/apiKey.ts` `computeApiKeyLimitPerMin`) — real per-plan budgets instead of one number for every partner: 60/min sandbox or Básico, 150/min Pro, 400/min Empresarial, and a standalone data-product key (Score API / PLD Screening API) gets its own 200/min tier independent of the account's subscription plan, since it's billed per call rather than gated behind one. A coarse, generous IP-based backstop (`apiKeyAbuseBackstop`) runs before authentication resolves, purely to bound the cost of hammering the key lookup itself — the real limit only applies once a key is known.
  - **Official SDKs** (`sdks/node`, `sdks/python`) — real, hand-written, zero-dependency clients (`@lastro/sdk` for Node/TypeScript, `lastro-sdk` for Python), one method per real `/api/v1` endpoint. Not published to npm/PyPI from this sandbox (no real registry account to publish under), but genuinely complete and tested end-to-end: each SDK's test suite starts the actual server (in-process for Node, as a real subprocess for Python) and drives every method against it over a live HTTP connection — see `sdks/README.md`.
- **Real webhook delivery with retry + delivery log** — partners register a URL + event (`duplicata.registrada`, `pagamento.confirmado`, `sinistro.decidido`, `block_trade.executado`, `rating.alterado`, …) from Desenvolvedores; the server does a genuine signed HTTP POST (HMAC-SHA256 over the body, `X-Lastro-Signature` header) when the event fires — same signing pattern Stripe uses for its own webhooks. Every attempt is logged to `webhook_deliveries` (visible per-webhook in Desenvolvedores as "Ver entregas"); a failed attempt is retried with backoff (immediate / 30s / 5min / 30min in production) before being marked permanently failed. A partner can rotate a webhook's signing secret at any time ("Rotacionar secret") without losing its registration or delivery history — the new value is shown once, and takes effect on the very next delivery.
- **LGPD data rights** — Perfil has an "Exportar meus dados" button (`GET /api/account/export`, a full JSON dump: profile, settings, duplicatas/aceites the account is a party to, notifications, ledger, API key/webhook metadata) and an "Excluir minha conta" flow (`POST /api/account/delete`, password-confirmed) that scrubs personal identifiers, revokes every refresh token/API key/webhook, and anonymizes the account row — financial/audit records tied to it stay intact (anonymized) rather than being deleted outright, since removing them would corrupt other parties' records.
- **Growth** — liquidity and distribution features, not just the core marketplace:
  - **Mercado Secundário** (`/app/secundario`, investidor-only) — resell a purchased duplicata before vencimento; another investor buys it at the agreed price, closing out the seller's position (kept in history) and opening a fresh one for the buyer. `POST /api/secundario/listar`, `GET /api/secundario`, `POST /api/secundario/:id/comprar`.
  - **Cestas de Investimento** (`/app/cestas`) — one-shot "invest R$X" flow: pick Conservadora (AA/A), Diversificada (all ratings) or Agressiva (B/C), and the platform greedily buys whole matching offers (best score first) until the budget runs out. `POST /api/cestas/investir`.
  - **Programa de indicação** — every account gets a unique referral code/link (Perfil); a referred signup grants the referrer +1 monthly emissão on the Básico plan, immediately. `GET /api/referral`.
  - **Página de transparência** (`/transparencia`, public) — live-computed platform stats (volume emitido/financiado, taxa de inadimplência, tempo médio até liquidação) straight from the database, not marketing copy. `GET /api/public/stats`.
  - **Status page** (`/status`, public) — a real background self-check (`src/lib/healthMonitor.ts`) pings the database every ~60s and logs the result to `system_health_checks`, so uptime/history are genuine, not a static badge. `GET /api/public/status`.
  - **Embeddable widget** — a chrome-less `/embed/simulador` page (iframe-able on a partner's own site) computing a real antecipação rate estimate via the same model as Emitir Duplicata, no auth or API key required. Snippet shown in Desenvolvedores. `POST /api/public/simular`.
- **Fighting market fragmentation** — the Brazilian duplicata-escritural market has 4 BACEN-authorized registradoras and every platform's risk data lives siloed to itself. Two features attack that directly:
  - **Multi-registradora smart routing** (`lib/registradoras.ts`) — a real router picks the cheapest registradora (B3/CERC/Núclea/Grafeno) for each emission, falling back to a more reliable-but-pricier one above R$200k where a failed/slow registration is costlier to redo. The chosen registradora is stored per duplicata and surfaced in the emit confirmation, `GET /api/v1/duplicatas/:id`, and a breakdown on the transparency page — instead of every integration hardcoding a single registry.
  - **Shared network risk-score** (`lib/riscoCore.ts` + `sacado_network_signals` table) — the real fragmentation fix for credit data: `GET /api/v1/sacados/:cnpj/score` blends Lastro's own SACADOS history with signals partners report via `POST /api/v1/sacados/:cnpj/sinais` (pagamento pontual / atraso / protesto / contestação), weighted by how much network evidence exists. A CNPJ that has *never* transacted on Lastro directly can still get a real (if low-confidence) score purely from what partners have reported about it. Real aceite outcomes on Lastro itself auto-seed the same pool, so the network isn't only as good as external contributions — it starts warm from Lastro's own activity. The internal Análise de Risco screen benefits from the same blend, not just the public API.
- **Validated API** — every mutating endpoint validates its body with Zod and returns structured 400s.
- **AI assistant** — `/api/chat/ask` calls the Anthropic API when `ANTHROPIC_API_KEY` is set, and falls back to canned answers otherwise so the app works out of the box without a key.
- **Structured logging + error tracking** — `pino`/`pino-http` request logging, optional Sentry (`SENTRY_DSN`) with a no-op fallback when unset.
- **Three-tier test suite + CI** — server unit/integration tests (Vitest + Supertest, including simulated-mode billing flows and a real Stripe webhook signature-verification test), client component tests (Vitest + React Testing Library), and Playwright E2E tests covering login, the marketplace buy flow, the full cedente→sacado emitir/aceite lifecycle, and the plan-gating→upgrade→unlock flow. `.github/workflows/ci.yml` runs all of it — typecheck, all three test tiers, and both builds — on every push and PR.
- **Accessibility** — modals trap focus and close on Escape, dropdowns are keyboard-dismissible, form fields use associated `<label>`s (with a correctness fix so an explicitly-`id`'d child still gets the right `htmlFor`), nav uses `aria-current`/`aria-expanded`.
- **Error boundaries + loading skeletons** on every authenticated page.
- **Docker** — a multi-stage `Dockerfile` + `docker-compose.yml` (app + optional Redis) that builds and serves the whole app — client and API — from one container.

### Real-when-configured integrations (revenue/growth pass)

A follow-up pass closed the gap between "demo" and "real business" wherever that's actually buildable in software, following the same pattern already established for Stripe/SMTP/Anthropic: real HTTP calls to the real provider when credentials are configured, a clearly-logged simulated fallback when not — never a silent no-op pretending to be real. See `server/.env.example` for every variable.

- **Automação de Lances is now real** — it used to draw from a static demo array and roll dice on whether to "apply." It now evaluates the investor's actual configured rules (score mínimo, taxa máxima, exposição por sacado, exposição mensal, diversificação por rating/setor) against the real open marketplace and, when an offer passes, performs the exact same purchase a manual "Comprar" click would (`lib/settlement.ts`). This was the single most urgent fix: it's a paid Pro-plan feature that previously did nothing real.
- **Real Pix payment rail** (`lib/paymentRail.ts`, `PIX_PSP_*`) — implements the actual BACEN "API Pix" contract (cobrança imediata, webhook confirmation) plus a payout call. Conta & Liquidação's deposit/withdraw flow replaces the old hardcoded fake bank-account string with a real Pix key on file, a real cobrança/QR code, and a real webhook (`POST /api/public/pix-webhook`) that credits the ledger on payment. Without a PSP configured, deposits need a manual "Confirmar (simulado)" click instead of a webhook — same idea as Stripe's simulated plan changes.
- **Real registradora integration** (`lib/registradoras.ts`, `REGISTRADORA_<CERC|B3|NUCLEA|GRAFENO>_API_URL/KEY`) — registration and duplicidade-check calls hit the actual configured registradora instead of only generating a local registro number. Unlike Pix (a public BACEN standard), each registradora's real API is a private commercial contract, so this is a reasonable generic REST shape meant to be adjusted once you have real API docs from them — not a verified copy of any one registradora's contract.
- **Real PLD/sanctions screening** (`lib/sanctionsFeed.ts`) — two additions ahead of the fictitious demo watchlist: `SANCTIONS_LIVE_FEED=true` screens KYB submissions against OFAC's real, free, public SDN list (no commercial account needed, off by default only to keep local dev/CI fast); `PLD_PROVIDER_API_URL/KEY` plugs in a licensed commercial PLD/KYC provider (Serasa Compliance, Quod, etc.) ahead of both, for real production compliance.
- **Real credit bureau blend** (`lib/creditBureau.ts`, `BUREAU_API_URL/KEY`) — Análise de Risco and the public score endpoint blend in a real external bureau score (Serasa/Boa Vista/Quod) on top of the existing internal + network-signal score, when configured.
- **Real Omie ERP connector** (`lib/erpConnectors/omie.ts`) — unlike the other adapters above, this doesn't need a Lastro-side commercial contract: any cedente with their own Omie account can enter their real `app_key`/`app_secret` in Integrações ERP, which validates against Omie's actual API and can then pull real contas a receber to prefill Emitir Duplicata. SAP/TOTVS stay as clearly-labeled "em breve" placeholders (no equivalent free self-serve API for either).
- **Real WhatsApp/SMS via Twilio** (`lib/smsNotifier.ts`, `TWILIO_*`) — an opt-in channel (Perfil) alongside email for every existing notification event, plus a new background job (`lib/aceiteReminder.ts`) that sends one urgent WhatsApp reminder when a sacado is down to 2 days left on the 15-day aceite window — the single biggest legal/UX risk in the flow, and a window email alone is a weak channel for.
- **Real Web Push notifications** (`lib/webPush.ts`, `VAPID_*`) — see below.

### Web Push notifications (`lib/webPush.ts`)

A fourth real notification channel alongside email/WhatsApp/in-app, using the actual W3C/IETF Web Push standard (RFC 8030 push protocol + RFC 8292 VAPID, via the `web-push` npm package) — not a vendor-specific API, so unlike `lib/esignature.ts` there's no "which provider's exact contract" ambiguity: any standards-compliant browser (Chrome, Firefox, Edge, Safari 16+) understands this on the receiving end for real. Wired into `db/misc.ts`'s `addNotification` — the single choke point every existing notification (leilão, aceite, disputa, admin fan-out) already goes through — so every one of those call sites gets real push delivery automatically, with zero changes needed at any of them.

A real `client/public/sw.js` service worker (no caching, no offline support — it exists solely to receive `push` events and show/route notification clicks) plus a genuine browser opt-in flow in Perfil: `Notification.requestPermission()`, `serviceWorker.register()`, `pushManager.subscribe()` with the real VAPID public key fetched from the server, then the resulting subscription posted to `POST /notifications/push/subscribe`. The toggle only renders when the server reports `VAPID_PUBLIC_KEY/PRIVATE_KEY` configured — no button that would silently do nothing. A dead subscription (404/410 from the push service — browser uninstalled, permission revoked) is cleaned up for real, not left as a stale row. Generate a real key pair with `npx web-push generate-vapid-keys` from `server/`.

`server/test/web-push.test.ts` (6 tests): reports disabled/no key when unconfigured; a subscription is stored and upserts (not duplicates) on the same endpoint; unsubscribe removes it; payload validation; `sendWebPush` is a real no-op with nothing to send; `addNotification` never throws with a real subscription on file while unconfigured.

### Claude-assisted features (beyond the chat widget)

Before this pass, Claude (`ANTHROPIC_API_KEY`) only powered the chat widget (`routes/chat.ts`) — everywhere else the product "looked like AI" it was static copy. `lib/claude.ts` is now a shared client every feature below reuses (text + vision/document calls); every one of them recommends or assists rather than deciding autonomously wherever the decision has real financial/legal weight — the human (cedente, admin, seguradora) still makes the actual call, same as the admin already did for KYB/disputes before this pass.

- **Compliance AI Engine** (`lib/complianceEngine.ts`) — the signals below (duplicidade, PLD, valor anômalo, score do sacado) used to live on separate screens with no unified decision. Now every emission gets a single 0–100 compliance score, computed by a **deterministic, auditable formula** over those same real signals — never an LLM free-floating number, precisely so the score stays reproducible with or without an API key. Claude's only role is generating the human-readable `reasoning` a reviewer sees (`compliance_engine_results.reasoning`); it never changes the score or the decision. A score ≥ the suspend threshold (default 80, **admin-configurable** at runtime — `GET/PUT /admin/compliance-threshold`, no code deploy needed, see `db/platformSettings.ts`) sets the duplicata to `status='suspensa_compliance'` — held out of `aprovada`/the marketplace — and routes it to a new **Fila de Compliance** in the back-office (`GET/POST /admin/compliance-queue`) where an admin liberates or rejeita it. This is always a suspend-for-review, **never an automatic permanent block** — same human-in-the-loop principle as every feature below, just with a real routing/blocking mechanism behind it instead of only a recommendation.
- **Real NF-e field extraction** (`lib/nfeExtraction.ts`) — replaces the old hardcoded fake extraction (`kind: 'nfe'` uploads always returned the same sample sacado/CNPJ/valor regardless of the file) with a real read of the uploaded NF-e: Claude vision for PDF/PNG/JPEG, direct XML parsing for XML (more reliable than vision for structured markup). Returns `null` — not a fabricated guess — when extraction fails, so Emitir Duplicata falls back to manual entry exactly like before.
- **Real contract clause analysis** (`lib/contractAnalysis.ts`) — Compliance's "Leitura de contratos" card (previously always the same 3 fixed demo lines, labeled "Simulado" in the UI) now analyzes a real uploaded contrato de cessão (`kind: 'contrato_cessao'` upload) for clauses incompatible with a duplicata escritural sale — vedação à cessão, exclusividade, confidencialidade que impeça registro. Persisted per user (`contract_analyses` table) so the real analysis reappears on reload; the "Simulado" badge only shows before the first real upload.
- **Real AI risk narrative** (`riscoCore.ts`'s `applyAiNarrative`) — the "sinais de IA" card in Análise de Risco (previously 3 fixed lines per stage 1/2/3, identical for every sacado at that stage) is now a real Claude synthesis of *that specific sacado's* actual score, rating, factors, network signals and bureau data. Falls back to the original canned text — not a fabricated narrative — when unavailable.
- **Dispute arbitration copilot** (`lib/disputeCopilot.ts`) — on-demand summary + suggested verdict (cedente/sacado/inconclusivo) with reasoning, computed from the dispute's actual motivo + message timeline. Since the "Connecting `disputa_sinistro` to the admin's real queue" pass below, this is served from inside `disputa_sinistro`'s `avaliar_disputa` tool via the agent card embedded in `DisputasPanel.tsx` — no longer a standalone `GET /admin/disputes/:id/ai-summary` endpoint. The admin still calls `POST /admin/disputes/:id/resolve` themselves (or approves the agent's `resolver_disputa` proposal) — the agent never decides on its own.
- **Sinistro triage copilot** (`lib/sinistroCopilot.ts`, `GET /seguradora/sinistro/:duplicataId/ai-triagem`) — flags real inconsistencies (aceite still pending, an unresolved dispute, days-overdue) for the seguradora to review before approving/denying a claim — same on-demand, human-decides pattern.
- **PLD second opinion on ambiguous matches** (`lib/pldSecondOpinion.ts`) — every PLD source that matches by plain substring (OFAC live feed, the demo watchlist) risks false positives (a shared surname, a generic word). Before such a match becomes an actual KYB flag, Claude judges whether the queried name and the matched entry plausibly refer to the same real entity. Only ever narrows a match to "not flagged" — never widens or invents one — and defaults to keeping the original match standing when Claude is unavailable or errors, so nothing about PLD screening gets weaker without a key configured. A paid PLD provider's own match (not a substring match Lastro computed) is never second-guessed this way — that's already an authoritative external decision.

### Agentes de IA (agentic)

Every feature above is one prompt in, one answer out — a single `askClaude()` call. This layer is different: an **agent** gets a real tool belt (functions that read or write actual Lastro data) and a loop (`lib/agentRuntime.ts`) — propose a tool call, execute it, see the result, decide the next step, repeat, until it has enough to answer or hits the step limit (default 8). `askClaudeWithTools` (`lib/claude.ts`) is the tool-use-capable call this loop drives; every step (what the model said, which tool it called, what came back) is logged to `agent_runs`/`agent_steps` for audit.

The one hard rule: **any tool that writes something with real consequence — money, a compliance/KYB decision, an official legal/regulatory record — is marked `sensitive` and never executes automatically**, no matter how confident the model is. The runtime parks the call in `agent_pending_actions` instead; a human (admin) has to explicitly approve it (`POST /agents/pending/:id/approve`, which runs the exact real handler with the exact input proposed) or reject it (`POST /agents/pending/:id/reject`, which never runs it). Read-only investigation tools execute immediately — that's what makes the agent actually investigate instead of just asking permission for every step.

Without `ANTHROPIC_API_KEY`, an agent run does **not** silently execute tools on a fixed script — it stops immediately in an honestly-labeled `mode: 'simulado'` run, same fallback philosophy as every single-shot feature above.

12 agents are registered (`lib/agents/*.ts`), each wrapping real existing pipelines/data as tools, surfaced in the back-office's **Agentes IA** tab (admin-only for now):

| Agente | O que investiga | Ação sensível (aprovação humana) |
|---|---|---|
| Emissão (`emissao`) | Duplicidade + risco do sacado antes de emitir | `emitir_duplicata` — registra na registradora de verdade |
| Underwriting (`underwriting`) | Score interno, bureau, histórico judicial, Open Finance | *(sem ação — só parecer)* |
| PLD/AML (`pld`) | Sanções/PEP, histórico judicial, alertas existentes | `sinalizar_pld` — flag de PLD na conta |
| Cobrança (`cobranca`) | Elegibilidade para cobrança jurídica | `escalar_cobranca` — gera e registra notificação/protesto/execução |
| Disputas & Sinistros (`disputa_sinistro`) | Histórico de disputa, triagem de sinistro | `resolver_disputa` — registra o veredito final |
| Regulatório (`regulatorio`) | Impacto de um normativo (BACEN/CVM/COAF) | `registrar_nota` — nota regulatória oficial |
| Onboarding/KYB (`onboarding`) | Sanções/PEP + judicial de uma empresa em análise | `aprovar_kyb` / `rejeitar_kyb` |
| Auto-Bid (`autobid`) | Regras do investidor vs. uma oferta específica | `comprar_oferta` — compromete capital real |
| Suporte (`suporte`) | Status real de duplicata/aceite/conta | `reenviar_lembrete_aceite` — envia WhatsApp real |
| Comercial (`comercial`) | Perfil/indicações de uma conta recém-cadastrada | `registrar_nota_comercial` — nota permanente no audit log |
| Market Maker (`market_maker`) | Anúncios do mercado secundário sem nenhum lance | `dar_lance_liquidez` — compromete capital real fornecendo liquidez |
| Reconciliação (`reconciliacao`) | Confirmações reais de Pix/boleto/TED sem lançamento correspondente no extrato | `marcar_resolvido` — encerra um alerta após revisão humana |

**Self-service access** (`AgentDefinition.selfServiceRoles`) — admin can run any of the 12 against any account, but three agents are also exposed directly to the role they serve: a **cedente** gets the Emissão agent embedded right in Emitir Duplicata, an **investidor** gets the Auto-Bid agent embedded in Automação de Lances, and the same investidor gets the Market Maker agent (opt-in, Automação de Lances) providing liquidity on the secondary market (`components/agents/SelfServiceAgentCard.tsx`). `routes/agents.ts` forces `actingUserId` to the caller's own id server-side regardless of what the request sends — self-service can never run an agent "as" someone else. Approval is scoped the same way: `emitir_duplicata`, `comprar_oferta` and `dar_lance_liquidez` are marked `selfApprovable`, so the owning user can confirm their own agent's proposal (the same effect as submitting the form / clicking "Comprar" / giving a lance manually) without needing an admin — but every other sensitive tool (PLD, KYB, legal/regulatory) stays admin-only no matter whose run it came from. The Market Maker agent's sensitive tool goes one step further than the others: it doesn't even accept a `userId` parameter from the model — the acting account always comes from the run's own context, never from what the LLM chose to pass, removing an entire class of "what if the prompt said a different id" risk rather than relying on the prompt alone to stay consistent.

**Cobrança agent as the actual régua** (`lib/cobrancaAgentJob.ts`) — instead of only running on a button click, a background job (`startCobrancaAgentJob`, every 6h) scans overdue duplicatas and lets the Cobrança agent decide per case whether to propose an escalation — same agent, same `escalar_cobranca` gate, nothing sends for real without admin approval. A dedup guard (`hasRecentAgentRun`) skips a case already investigated in the last 24h so the job doesn't re-spend tokens on the same duplicata every cycle; when it proposes anything new, every admin gets an in-app notification (`db/misc.ts`'s `notifyAdmins`) pointing at the Agentes IA queue. A no-op (not even a wasted run) without `ANTHROPIC_API_KEY`, same discipline as every agent.

**Onboarding agent as KYB pre-triage** (`routes/auth.ts` `POST /kyb`) — submitting KYB now also kicks off the Onboarding agent in the background (fire-and-forget, never blocks the response): it investigates sanções/PEP and histórico judicial and, when confident, proposes `aprovar_kyb`/`rejeitar_kyb` as a normal gated pending action. The admin KYB queue (`GET /admin/kyb`) surfaces that run's summary and, if a recommendation is pending, a one-click "Confirmar recomendação" that goes through the exact same `/agents/pending/:id/approve` gate as running the agent by hand — the admin still makes the actual call, the agent just does the legwork first.

**Market Maker agent as the automated liquidity source** (`lib/marketMakerAgentJob.ts`) — same periodic-scan shape as the Cobrança/PLD jobs, but self-service by design: every 6h it re-scans investidor accounts that opted in (`settings.marketMakerEnabled`, toggled from Automação de Lances alongside the existing Auto-Bid rules — `POST /automacao/market-maker/toggle` / `/rule`) and lets the agent evaluate secondary-market listings with zero active bids against that investor's configured score minimum and exposure cap (`marketMakerMinScore`/`marketMakerMaxExposicao`), proposing liquidity-providing bids at a computed fair value (`lib/dynamicPricing.ts`'s real rate-band estimate, never above the listing's own asking price). `dar_lance_liquidez` stays sensitive but `selfApprovable` — the investor gets a notification and approves their own proposed bids from Agentes IA, the same self-service shape as Auto-Bid, just running on a schedule instead of only per-offer. A dedup guard skips an investor's book already scanned in the last 6h. A no-op without `ANTHROPIC_API_KEY`, same discipline as every agent.

**Reconciliation Agent** (`lib/reconciliation.ts`, `lib/agents/reconciliation.ts`) — every payment rail (Pix/boleto/TED) confirms money moved by flipping a status on its own table (`db/pix.ts`/`db/boletos.ts`/`db/ted.ts`); a separate write puts the matching entry in the user's `ledger` extrato. Those two writes aren't one transaction today, so `rodar_reconciliacao` scans the last N days of *real* (non-`simulado`) confirmations for exactly the failure mode where one happened without the other (matched on user + valor + a 10-minute timestamp window, since no shared reference id exists between a rail confirmation and its ledger row), raising a `reconciliation_flags` row for anything unmatched. `marcar_resolvido` is sensitive/admin-only — the agent investigates and explains, it never closes its own findings. Exposed at admin-only `GET/POST /api/reconciliation/*` and the back-office's **Reconciliação** tab (manual "Rodar reconciliação agora" button today, not yet on a cron — see Known gaps).

**Governance** (`lib/agentGovernance.ts`) — a per-agent kill switch (admin can disable any of the 12 without a deploy), an optional daily USD budget per agent (checked before any run starts, reusing the real token-cost metering already in `db/claudeUsage.ts`), and a configurable BRL threshold above which a sensitive tool's *admin-approved* action needs two distinct admins instead of one (`AgentToolDef.extractValueBRL`, wired for `emitir_duplicata`/`comprar_oferta`/`dar_lance_liquidez`) — self-service approval by the account owner is never subject to this, it already mirrors an unassisted action. All three live in the admin "Agentes IA" tab's collapsible Governança panel.

**Handoff + cross-agent memory** — `createHandoffTool` (`lib/agentRuntime.ts`) gives an agent a generic `acionar_agente` tool to call another registered agent mid-investigation (wired for Emissão → Underwriting on an ambiguous risk read, and Cobrança → Disputas & Sinistros when it finds an open dispute), capped at one level deep so it can't loop. Separately, any run against a `subjectType`/`subjectId` (e.g. a duplicataId) automatically pulls in the summaries of every prior *completed* run against that same subject — regardless of which agent produced them — so a second agent looking at the same case isn't starting blind.

### Platform hardening (rate limiting, cost metering, real team accounts, real 2FA)

- **Rate limiting on every Claude-calling route** (`lib/aiRateLimit.ts`) — chat, NF-e/contract analysis, the risk narrative, the dispute/sinistro copilots, and PLD second opinion (via KYB) all share one limiter: 30 requests/15min, keyed per authenticated user (not per IP, so it can't be bypassed by a shared office/NAT IP and doesn't penalize other users on it). Each of these is a real, metered Anthropic API cost — see the next point — so this is cost/abuse control, not just spam prevention.
- **Claude usage/cost metering** (`db/claudeUsage.ts`, `GET /admin/ai-usage`) — every call through `lib/claude.ts` (now including the chat widget, refactored onto the same shared client) logs the real token counts the Anthropic API returned, tagged by feature and, where available, by user. The admin back-office's **Uso de IA** tab shows totals and a per-feature breakdown, with an approximate USD cost estimate (rate configurable via `CLAUDE_COST_INPUT_PER_MTOK_USD`/`CLAUDE_COST_OUTPUT_PER_MTOK_USD` — real token counts, estimated $/token) — enough to see which feature or user is driving spend without leaving the app.
- **Real team invites** (`db/misc.ts`, `routes/profile.ts`, `routes/auth.ts`) — Perfil's "Equipe" used to just store a decorative nome/email row with no real account behind it. Inviting someone now generates a random single-use token (only its SHA-256 hash is ever stored), emails an accept link (`POST /profile/team/invite` — logged instead of sent, and returned in the response too, when `SMTP_HOST` isn't set, same fallback pattern as every other notification here), and accepting it (`POST /auth/team-invite/accept`, public) creates a **real, login-capable account** linked to the owner via `users.team_owner_id`. Team-member accounts get read-only access to Dashboard, Minhas Duplicatas, Histórico and Receita only — enforced centrally in `auth/middleware.ts` (every other GET is 403'd, every write is 403'd except the account's own profile/notification/2FA self-service) — and their nav is scoped down to match, so the UI never shows a tab that would just 403. An owner can revoke a member at any time (`POST /profile/team/:id/revoke`), which locks the account out immediately, not just once its current access token expires.
- **Real TOTP-based 2FA** (`lib/totp.ts`, RFC 6238 — no external dependency) — `POST /auth/2fa/setup` generates a secret (shown as text + an `otpauth://` URL for manual entry into Google Authenticator/Authy/1Password/etc. — no QR image, same fallback those apps themselves offer), `POST /auth/2fa/confirm` proves possession before actually enabling it and returns 8 one-time recovery codes (only their hashes are stored). Once enabled, `POST /auth/login` returns a short-lived challenge token instead of real session tokens when the password is correct — `POST /auth/2fa/verify-login` exchanges it (plus a TOTP or recovery code) for the real ones. The challenge token is a distinctly-typed JWT (`auth/jwt.ts`) that `requireAuth` explicitly refuses to accept as a normal access token, so knowing only the password is never enough to reach any real endpoint.

### Legal AI (Jurídico panel)

A duplicata escritural is a **título executivo extrajudicial** (Lei 5.474/68 art. 15 c/c CPC art. 784, I) — a real ação de execução can be filed directly against an inadimplente sacado, without first needing a full ação de conhecimento to prove the debt. These four modules assist a human on that path; none of them files, sends, protocols or decides anything on its own, and the OAB (Estatuto da Advocacia, Lei 8.906/94) reserves legal practice to a licensed advogado — so every generated document carries a fixed, deterministic disclaimer (`LEGAL_DRAFT_DISCLAIMER`, never left to the LLM to remember to include) requiring advogado review and signature before any formal use, and every draft is logged (`legal_documents` table) with a reviewed/not-reviewed status an admin tracks explicitly.

- **Assistente de cobrança jurídica** (`lib/legalCollection.ts`, admin **Jurídico → Cobrança Jurídica**) — surfaces overdue duplicatas and drafts, on demand: a notificação extrajudicial de cobrança, a minuta de indicação a protesto, and a rascunho de petição inicial de execução, all populated from the duplicata's real registered data. Eligibility is a deterministic gate, not an LLM judgment call: the sacado must actually be overdue, the aceite must be confirmed (`aceita`), and there must be no unresolved dispute — enforced both when listing candidates and again on generation (`checkCollectionEligibility`).
- **Verificação de histórico judicial** (`lib/judicialRecords.ts`) — real-when-configured adapter for a commercial judicial-records provider (Escavador/Jusbrasil-style — there's no free official public API for this in Brazil, unlike OFAC's sanctions list). When `JUDICIAL_RECORDS_API_URL/KEY` is set, an open execução or falência/recuperação judicial against the sacado's CNPJ becomes a real new factor in the Compliance AI Engine's score (`lib/complianceEngine.ts`); unconfigured, it's simply never added — no fabricated signal.
- **Monitor de conformidade regulatória** (`lib/regulatoryMonitor.ts`, admin **Jurídico → Regulatório**) — deliberately *not* an automated scraper: an admin pastes the actual text of a normativo (resolução BACEN, circular, etc.) and Claude summarizes it, flags impact areas, and suggests actions, stored in `regulatory_notes` for the admin to acknowledge. Every note traces back to a real text a human supplied — there's no honest way to build a live BACEN/CVM/COAF feed in this environment, so this doesn't pretend to.
- **Gerador de minutas jurídicas** (`lib/legalDraftGenerator.ts`, admin **Jurídico → Minutas**) — lower-stakes standalone drafts (resposta a titular de dados/LGPD, comunicado de atualização de termos, notificação padrão) from a short admin-supplied context, same draft-only/human-reviews principle as cobrança jurídica.
- **Fee de sucesso sobre valor recuperado** (`lib/legalCollectionFee.ts`, admin **Jurídico → Cobrança Jurídica**) — a real new revenue line: once an admin marks a duplicata escalated to cobrança jurídica as recuperada (`POST /admin/juridico/cobranca/:id/recuperar`), Lastro charges an admin-configurable % (default 5%, `GET/PUT /admin/juridico/cobranca-fee`) of the recovered value against whoever currently holds the receivable — the cedente if it was never sold, or the investidor currently holding it (even after a mercado secundário resale, resolved via `currentCreditorFor`) if it was. Only ever charged once per duplicata; the fee is a real ledger debit (`legal_collection_fees` table, surfaced in Modelo de Receita alongside the platform fee and insurance commission), while the recovery itself (the sacado's actual payment) happens outside the platform, same "real accounting, simulated money movement" scope as the rest of the settlement layer. Marking a duplicata recovered also sets its status to `paga` — the first real flow that uses that status, previously only present in static demo seed data.
- **Assinatura eletrônica real-when-configured** (`lib/esignature.ts`) — closes the gap between "Claude drafted a real document, a human reviewed it" and "it's actually signed", which this codebase never did before: any reviewed `legal_documents` row (a minuta geral or a cobrança jurídica document) can be sent to a real signer. Deliberately generic instead of hardcoded to one vendor's exact API shape (same reasoning as `lib/biometricKyc.ts`'s provider-agnostic adapter — e-signature providers like Clicksign/DocuSign/D4Sign/Adobe Sign each have their own real contract, and guessing one specific vendor's endpoints wrong would silently break against whoever's actually configured): `ESIGNATURE_API_URL`/`KEY` point at a REST endpoint this adapter calls with a documented-but-adjustable shape. Unconfigured (the default here), every send is simulated and clearly labeled (`simulado: true`, `esignatureConfigured: false` in the response) rather than faked as real. A document must be reviewed first (the same human-review gate every legal draft already enforces) and the admin supplies who's actually signing — nothing auto-discovers a counterpart's email. `POST /admin/juridico/documentos/:id/assinatura[/status]`; signer name/email inputs and status badges on the Minutas panel.

  `server/test/legal-signature.test.ts` (6 tests): refuses an unreviewed document; sends a reviewed one (simulated) and reports it honestly as unconfigured, not fake-real; rejects sending the same document twice; checks and updates status (simulated mode resolves to `assinado`, since there's no real callback URL reachable from this sandbox); rejects a status check for a document never sent; validates signer name/email.

### Closing competitive gaps (vs. Monkey/Kanastra-style platforms)

A follow-up pass built out the concrete, software-buildable gaps identified against established duplicata-escritural competitors — same real-when-configured-honest-fallback discipline as everything above; the two gaps that are genuinely not fakeable in this environment (a full institutional licensing stack, and the transaction *scale* those platforms have from years of production volume) are deliberately left out rather than simulated.

- **Real SAP/TOTVS ERP connectors** (`lib/erpConnectors/sap.ts`, `lib/erpConnectors/totvs.ts`) — same self-serve model as the existing Omie connector: no Lastro-side commercial contract needed, a cedente enters their own SAP Business One Service Layer credentials (base URL/company DB/user/password) or TOTVS OAuth2 client credentials in Integrações ERP, which are validated against the real API contract (SAP's `/b1s/v1/Login` + `Invoices` OData filter; TOTVS's `/authorization/v1/token` + `contas-a-receber`) and can then pull real contas a receber to prefill Emitir Duplicata, closing the "em breve" placeholder from the earlier Omie pass.
- **Emissão automática via ERP** (`lib/autoEmitJob.ts`) — an opt-in background job (Integrações ERP → "Emissão automática", off by default, capped by a configurable max valor per duplicata) that polls every connected ERP (Omie/SAP/TOTVS) every 30 minutes and, for each not-yet-imported contas a receber under the cap, runs it through the exact same `submitEmitir()` pipeline a manual emission uses — duplicidade check, Compliance AI Engine, registradora — never a shortcut around those gates. Each import is deduped per user+fonte+external ID (`auto_emit_imports` table) so nothing is ever double-emitted, and every run is logged to the existing automation-activity feed.
- **Real boleto payment rail** (`lib/boletoRail.ts`, `BOLETO_PSP_*`) — a second deposit method alongside Pix on Conta & Liquidação, gated the same way: a configured PSP contract emits a real boleto (linha digitável, código de barras) and a real webhook (`POST /api/public/boleto-webhook`) credits the ledger on payment; unconfigured, deposits fall back to an honestly-labeled simulated boleto with a manual "Confirmar (simulado)" click, mirroring the existing simulated-Pix fallback exactly.
- **White-label branding** (`routes/erp.ts`'s `/whitelabel/*`, Empresarial plan only) — a cedente on the Empresarial plan can set a nome/cor primária/logo that's honestly scoped to what's actually achievable without owning DNS/email-sending infrastructure: it relabels the WhatsApp aceite-deadline reminders their own sacados receive (`"{sua marca} (via Lastro)"` instead of `"Lastro"`) — not a full UI re-skin or outbound-email-identity change, which would need real domain/DKIM setup this repo can't provide. See "White-label — cada aceite notifica o sacado na hora" below for how this branding was later extended to a real, previously-missing notification.
- **Open Finance cash-flow signal** (`lib/openFinance.ts`, `OPEN_FINANCE_API_URL/KEY`) — blends a real sacado cash-flow signal (receita média mensal, volatilidade) from a configured Open Finance aggregator into Análise de Risco, on top of the internal + network + bureau score, the same additive-factor pattern as the credit bureau blend. Covers only the data-pull side of Open Finance (what a fully licensed integration would use once consent is already granted) — not the consent-redirect UX itself, which needs a registered Open Finance participant this repo can't be.
- **Biometric KYC / prova de vida** (`lib/biometricKyc.ts`, `BIOMETRIC_KYC_API_URL/KEY`) — a selfie upload (`kind: 'selfie_liveness'`) run through a configured liveness-detection provider replaces the old decorative "Verificação antifraude (KYC)" checklist line with a real Verificado/Pendente state (`users.settings.biometricVerified`); unconfigured, the item just stays honestly Pendente with an upload action, nothing is faked as verified.

### Production-readiness pass (backups, TED rail, real sandbox isolation)

A follow-up pass closed three gaps that matter specifically once real money is moving through the platform, not just feature completeness.

- **Automated SQLite backups** (`lib/backup.ts`, admin **Auditoria** tab) — the single most important gap of the three: until this pass there was no disaster-recovery story at all for the datastore backing every saldo, duplicata and audit record. A background job snapshots the live database every 6h (configurable via `BACKUP_INTERVAL_MS`) using SQLite's own online backup API (safe against a live WAL-mode database, not a naive file copy), retains the most recent 28 by default (`BACKUP_RETENTION_COUNT`), and optionally hands each snapshot to `BACKUP_OFFSITE_CMD` (e.g. `aws s3 cp`) for off-instance storage — no cloud credential is shipped by default. An admin can also trigger a snapshot on demand and see the list with sizes/timestamps.
- **Real TED payment rail** (`lib/tedRail.ts`, `TED_PSP_*`/`LASTRO_TED_*`) — a third deposit/withdrawal method on Conta & Liquidação alongside Pix and boleto, for large institutional transfers. Deliberately asymmetric from Pix/boleto: TED has no universal real-time confirmation contract, so there's no user-facing "confirmar (simulado)" button — a deposit is only ever confirmed by a real BaaS webhook (when `TED_PSP_*` is configured) or by an admin matching the real bank statement by hand (`GET/POST /admin/ted/*`), the same way TED reconciliation actually works at a fintech without a virtual-account BaaS product in front of it.
- **Real sandbox data isolation for partner API keys** (`lib/sandboxData.ts`) — closes the previous gap where a test-mode key (`lastro_test_…`) read/wrote the exact same account data as a live key, just labeled differently. Duplicatas created via a test-mode key are now tagged `sandbox=1` and filtered out of every live/internal read path (Minhas Duplicatas, Marketplace, monthly emit-limit counting, seguradora claim queues) at the query layer in `db/duplicatas.ts`, and `/v1/duplicatas/:id` 404s on any cross-mode lookup. Generating a test key auto-seeds a small deterministic demo dataset so a partner has something to explore immediately, and a sandbox emission never touches a real registradora regardless of configuration. Extended to aceites (`GET/POST /v1/aceites*` respect the calling key's mode, cross-mode lookups 404) and disputes (a dispute raised against a sandbox aceite never surfaces in a real cedente's Disputas screen or the admin arbitration queue) in the "o que está faltando" pass — not yet extended to insurance sinistro sub-resources.

### "O que está faltando" pass (PLD monitoring, sandbox coverage, real Google login)

- **Automated suspicious-activity monitoring** (`lib/suspiciousActivityMonitor.ts`, admin **Compliance** tab) — a COAF-style detection layer on top of the real ledger, beyond the emission-time value-anomaly/NF-e-reuse alerts already in `lib/fraudDetection.ts`. Two deterministic rules run every 6h (same "deterministic core" principle as the Compliance AI Engine — no LLM involved in detection): **fracionamento** (3+ deposits within 24h, each under an admin-configurable threshold, summing above it) and **entrada/saída rápida** (a deposit followed by a similarly-sized withdrawal within 48h — classic layering). Real submission to COAF's SISCOAP gateway needs a licensed institution's credentials this repo can't have, so a flagged case is reviewed by an admin, who either dismisses it or records that they reported it externally (the real COAF protocol number goes in `external_reference`) — never a fabricated automatic submission.
- **Sandbox isolation extended to aceites and disputes** (`db/aceites.ts`, `db/disputes.ts`, `lib/aceiteCore.ts`) — the isolation added in the previous pass only covered duplicatas; a sandbox aceite (created automatically whenever a test-mode key emits a sandbox duplicata) could still have leaked into a real cedente's read-only aceite view or, if contested, into the admin's real dispute arbitration queue. Both are now filtered by the underlying duplicata's `sandbox` flag at the query layer, and `/v1/aceites/:id/status` 404s on any cross-mode id, mirroring `/v1/duplicatas/:id`.
- **Sandbox isolation extended to insurance sinistro claims** (`db/duplicatas.ts`'s `listInsuredByInsurerKey`/`listClaimableByInsurerKey`, `lib/seguradoraCore.ts`) — `GET/POST /v1/seguradora[/sinistro/:duplicataId/decidir]` used to always read/decide against the live data plane regardless of the calling key's mode, the one partner-facing claim-decision endpoint the aceites/disputes pass above didn't reach. Both now take a `sandbox` flag threaded from `req.apiKey!.mode === 'test'`, exactly like `listAceitesByCedente` — a test-mode seguradora key only ever sees/decides its own sandbox sinistros, a live key can't even resolve a sandbox sinistro's real id to act on it (404), and vice versa. `server/test/sandbox-isolation-sinistro.test.ts` (3 tests): a test key sees/decides its own sandbox sinistro invisibly to a live key on the same account; a test key 404s against a real sinistro's real id even knowing it; the internal SPA route never sees a sandbox sinistro.
- **Real "Entrar com Google"** (`lib/googleOAuth.ts`, `GOOGLE_OAUTH_CLIENT_ID/SECRET`) — a genuine OAuth 2.0 authorization-code flow against Google's actual endpoints, not a mocked identity. An existing email gets linked and logged in; a brand-new email gets a short-lived, Google-verified signup token (`POST /auth/google/complete-signup`) so role/companyName can still be collected before an account exists — the one piece of information Google can't provide. Unlike every other real-when-configured integration here, there's deliberately no simulated fallback: faking a third party's identity verification would be dishonest in a way simulating a payment or a registry number isn't, so the "Continuar com Google" button is simply hidden (`GET /auth/google/config`) rather than pretending to work.

### International investor onboarding groundwork (PLD, jurisdiction check, eligibility memo)

A follow-up pass answered a real question — "how do we legally offer these duplicatas to foreign banks/investors" — with actual regulatory research (Resolução Conjunta BCB/CVM 13/2024, which replaced Resolução CMN 4.373/2014 on 1 Jan 2025; Res. CVM 160/2022; Res. CVM 50/2021; Lei 11.312/2006; IN RFB 1.037/2010; Lei 13.810/2019), then built the parts of that answer that are actually software, not licensing:

- **UN Security Council Consolidated List screening** (`lib/sanctionsFeed.ts`, same `SANCTIONS_LIVE_FEED` flag as OFAC) — unlike OFAC/EU, UN sanctions are directly, self-executingly binding in Brazil (Lei 13.810/2019 art. 4/7) regardless of any foreign counterparty, so this isn't just "nice to have" for INR onboarding — it's a real gap in the existing OFAC-only screening that got closed alongside it.
- **Non-resident investor (INR) fields on KYB** (`KybModal.tsx`, `routes/auth.ts`) — a "somos um investidor não residente" toggle swaps the CNPJ field for país de domicílio, ID fiscal estrangeiro and o representante autorizado pelo Banco Central que a Res. Conjunta 13/2024 art. 6 exige.
- **Low-tax-jurisdiction check** (`data/lowTaxJurisdictions.ts`) — a point-in-time snapshot of the real IN RFB 1.037/2010 list (jurisdições de tributação favorecida), since there's no free official API for it; determines whether the investor's country disqualifies them from the 0% IRRF treatment under Lei 11.312/2006.
- **Deterministic eligibility memo** (`lib/foreignInvestorCompliance.ts`, admin **KYB** tab) — an admin-triggered, non-LLM memo combining investor classification (Res. CVM 160/2022 art. 12 — institutional KYB types are treated as Investidor Profissional), the jurisdiction check, and enhanced PLD screening (Res. CVM 50/2021 art. 8 requires this specifically for INR clients). The memo carries a fixed disclaimer — never LLM-assembled, so it can't be silently dropped — stating plainly that Lastro is origination/technology only in this chain: a real offer of FIDC cotas to a foreign investor still requires a CVM-authorized fund administrator, a CVM-registered securities distributor, and a BCB-authorized FX institution, none of which this generates or replaces.

### Revenue expansion pass (usage billing, standalone data products, add-on subscriptions)

A follow-up to "what's missing, what can we sell inside the platform" — five revenue streams built on top of a single, reusable billing engine (`db/addOnCharges.ts` + `lib/addOnBilling.ts`, table `addon_charges`), so every add-on charge is a real ledger debit (`db/ledger.ts`) and a real row, same "real accounting, simulated money movement" pattern as the platform fee, insurance commission and legal-collection fee that came before it. Two billing modes cover every shape of add-on: `chargePerCall()` (always charges, no dedup — for pay-per-request products) and `chargeOncePerPeriod()` (idempotent per `user + kind + month` via a UNIQUE constraint — for flat monthly subscriptions, safe to re-run). Every price is admin-configurable (**Admin → Auditoria** tab) with a hardcoded default fallback.

1. **API usage overage billing** (`lib/apiOverageBilling.ts`) — the existing Empresarial-only partner API now has a monthly included-calls quota (admin-configurable, default 10,000); live, full-platform usage beyond it is billed automatically at month-close by a daily background job (always targeting the previous complete calendar month, safe to re-run). Test-mode usage stays free, as it already did for the sandbox dev tier. Usage/quota and the running estimate are shown live in **Desenvolvedores**.
2. **Risk Score API — standalone product** (`api_keys.product`, `GET /v1/sacados/:cnpj/score`) — a new `product` field on partner API keys (`'platform' | 'score_api' | 'pld_screening_api'`, default `'platform'` so every existing key is unaffected) lets a company that isn't a Lastro customer at all buy just the blended risk-score lookup, billed per call, with no plan requirement. A gating middleware in `routes/v1.ts` restricts a narrow-product key to only its one endpoint; a full `'platform'` key's score access stays covered by its subscription/overage billing, never double-billed.
3. **PLD/KYC screening as a service** (`POST /v1/pld/triagem`) — the same reuse-what's-already-real pattern applied to `db/sanctions.ts`'s OFAC + UN Security Council Consolidated List screening (already used internally for every KYB submission): sold standalone, per call, to a company that wants compliance screening without building it.

Requires a brand already configured and the Empresarial plan; once subscribed, the sacado's own in-app aceite view shows the cedente's brand instead of generic "Lastro" (`lib/aceiteCore.ts`), not just the outbound message.

### Real trained credit-scoring model (`lib/mlScoring.ts`)

`riscoCore.ts`'s score is a fixed-weight blend formula — this adds an actual trained model alongside it: a dependency-free logistic regression (plain gradient descent, no ML library — auditable line by line) fit on real labeled outcomes already in this codebase's own data (`sinistro_status='aprovado'` — a confirmed insurance payout — or `status='paga'` via legal collection recovery, both real state transitions the app already performs, never a fabricated label). Refuses to train below `MIN_TRAINING_SAMPLES` (12) or when every example shares the same label, rather than fitting noise and presenting it as a real model — until then, scoring behaves exactly as it did before this existed. Exposed as the Underwriting agent's `prever_probabilidade_ml` tool (returns "indisponível" honestly when untrained) and as an admin panel (**Admin → Uso de IA**) showing sample count, accuracy and a manual retrain button — this is also what backs the standalone Score API product as an actual data asset instead of only a static formula with a price tag on it.

### Network-anomaly fraud detection (`lib/fraudAnomalyDetection.ts`)

A complement to the existing per-transaction fraud checks (same-value-same-vencimento duplicidade, 3x-average valor anômalo) — those look at one duplicata at a time; this looks at the shape of a cedente's whole book. Computed fresh on every call (never persisted/stale) over real rows: **concentração anômala** flags a cedente whose emitted volume is ≥80% concentrated in a single sacado (a healthy book is spread across buyers — heavy concentration is the classic shape of related-party or fabricated invoicing), and **autorrelacionamento** flags a duplicata where the sacado's name is identical to the issuing cedente's own (a company appearing to sell to itself). `GET /admin/fraud-anomalies` exposes both live; the PLD agent has a `detectar_anomalias_de_rede` tool to pull findings for a specific company mid-investigation, and `lib/pldAgentJob.ts`'s autonomous scan (see "Agentes de IA" above) now feeds from these findings too, alongside SAR reports and compliance alerts.

### Dynamic auction pricing (`lib/dynamicPricing.ts`)

The deságio shown for a real duplicata was always a flat `2,5%` — `desagio` is set on the row only by the (never-actually-called-at-emission) parameter, so every marketplace listing fell back to the exact same fixed number regardless of rating or how tight capital actually was. This replaces that with a real 30-day supply/demand signal computed from the platform's own book (`duplicatas` emitted vs. `purchases` made in the last 30 real days), clamped to ±15–25% around each rating's base band (`BASE_RATE_BANDS`, moved here from `emitirCore.ts` as the single source of truth) so a data blip can't send a quoted rate to zero or double. Wired into both the pre-emission preview (`computeEmitirPreview`'s `taxaEstimadaFmt`, with the multiplier itself returned as `liquidezMultiplicador` for transparency) and the live marketplace base rate (`marketCompute.ts`'s `buildOfferView`) — the same real signal drives what a cedente is quoted before emitting and what investors actually see in the leilão.

### Request observability (`lib/metrics.ts`)

Real per-route latency (p50/p95) and error rate from this process's own request history — a bounded in-memory ring buffer (5,000 samples), honestly labeled as in-process only (resets on restart, doesn't aggregate across instances) rather than pretending to be a durable APM. `metricsMiddleware` (mounted early in `app.ts`) buckets by route *pattern* (`/agents/:agentId/run`, not the literal URL), so per-id traffic doesn't explode into unbounded cardinality. `GET /admin/metrics?windowMinutes=60` (admin-only) returns the live breakdown — good enough to answer "is this route slow, is this route erroring" today, without waiting on a real tracing/APM integration to exist first.

### Optional cache + a Postgres migration path (`lib/cache.ts`, `docs/postgres-migration.md`)

Same real-when-configured shape as `ws.ts`'s Redis pub/sub relay: `cacheGet`/`cacheSet`/`cached()` use real Redis when `REDIS_URL` is set, and fall back to a bounded in-memory TTL map otherwise — a cache failure (Redis down, whatever) is always a clean miss, never a broken request. Wired into the highest-traffic real public read, `GET /api/public/stats` (30s TTL — explicitly stated staleness, not hidden). `docs/postgres-migration.md` is a deliberately honest scoping document for the SQLite→Postgres question — not implemented here, but mapped against the real code (which files, which non-portable SQL, what changes vs. what doesn't) so the decision of *when* to migrate is informed rather than guessed at.

### Enterprise SSO/SAML (`lib/samlSso.ts`)

Real SP-initiated SAML 2.0 login against a real identity provider (Okta, Azure AD, Google Workspace, OneLogin…), using the `samlify` library. Same real-when-configured shape and account-linking flow as "Entrar com Google" above — `GET /auth/saml/config` reports whether it's on, `GET /auth/saml/login` redirects to the configured IdP, `POST /auth/saml/acs` verifies the returned assertion's signature against the IdP's real certificate (from `SAML_IDP_METADATA_XML`) and either logs in an existing linked account, links a matching-email account, or hands the client a short-lived signup token so role/companyName can be collected before creating a brand-new account (`POST /auth/saml/complete-signup`). No simulated fallback, for the same reason as Google OAuth: faking a third party's signed identity assertion would be dishonest, so "Entrar com SSO corporativo" is simply hidden on the client when `SAML_IDP_METADATA_XML`/`SAML_SP_ENTITY_ID` aren't set. One deliberate implementation choice worth calling out: the XML schema validator samlify requires is a lightweight well-formedness check here, not full XSD validation — the maintained XSD validators shell out to a bundled JVM, which would silently add a Java runtime requirement to the Docker image just to accept a login. This does not weaken the actual anti-forgery boundary (the assertion's signature is still verified for real, by samlify itself, against the IdP's real public key) — see the comment in `lib/samlSso.ts` for the full reasoning. Not tested against a live enterprise IdP in this sandbox (there isn't one available here to test against), same honest caveat as every other real-when-configured integration in this codebase that depends on a counterparty this environment can't provide.

### Secondary market depth + institutional block trades (`lib/resaleCore.ts`, `lib/blockTrade.ts`)

The secondary market (`routes/secundario.ts`) was a fixed-price classifieds board — a seller posts an asking price, a buyer either pays it or doesn't. Two real additions:

- **Market depth (bids).** A buyer can now place a bid below/at/above a listing's asking price (`POST /secundario/:id/lances`) instead of only accepting it outright — the seller decides whether to accept (`POST /secundario/lances/:bidId/aceitar`, trade executes at the *bid's* value, not the asking price) or reject it. A bidder holds at most one active bid per listing — raising it replaces the old one rather than stacking a second row. The public market view shows the best (highest) active bid alongside the asking price, real top-of-book depth, without exposing bidder identity to anyone but the seller — who sees the full bid book on their own listings. New `resale_bids` table (migration `0033_secondary_market_depth.sql`).
- **Institutional block trades.** `POST /secundario/block-trade` sweeps several active listings at once against one buyer's criteria (budget, minimum score, max count) in a single transaction — restricted to accounts that declared a patrimônio líquido above an institutional threshold on KYB, and subject to a minimum aggregate size below which it's just a regular purchase wearing a fancier name. Every swept listing is still bought at *exactly* its posted asking price — the buyer's volume perk is a discount on the platform's own fee, never a markdown on what a seller was owed (see `settleResale`'s `feeDiscountPct`). Greedy best-value-first matching (biggest discount-to-face-value listings first), honestly documented as a reasonable heuristic, not a claim of optimal execution. New `block_trades`/`block_trade_items` tables for a real audit trail (who bought what, at what price, in which sweep).

Both share the same trade-execution path as the original outright-buy flow (`executeResaleTrade`), so settlement/ledger/notification behavior stays consistent across all three ways a resale position can change hands.

### Feature flags administráveis (`lib/featureFlags.ts`, admin **Feature flags** tab)

A code-defined registry (`FEATURE_FLAG_DEFS`) of real operational kill switches, each with its own default and each checked at a genuine call site — not a catalog nobody reads. An admin toggle overrides the code default at runtime (`feature_flags` table, migration `0034_feature_flags.sql`); with no override the app behaves exactly as if the system didn't exist. Ships with four real gates:

Also supports a deterministic percentage rollout (`rolloutPct`, hash of flag key + user id, so a given user always lands on the same side instead of flipping between requests) for any future flag that needs a gradual ramp rather than a hard on/off. `GET/POST /admin/feature-flags[/:key]`.

### Questionário de suitability do investidor (`lib/suitability.ts`, investidor **Perfil de Investidor**)

A CVM-style suitability (adequação) questionnaire — a real, deterministic point-scored assessment (6 questions covering objetivo, horizonte, tolerância a perdas, experiência, concentração patrimonial e estabilidade de renda; every point traces to a single answer, no black box) that classifies an investor as **conservador / moderado / arrojado**, valid for 24 months (`suitability_assessments` table, migration `0035_suitability.sql`). `GET/POST /suitability`.

The real gate this feeds: **cestas de investimento** (`lib/cestasCore.ts`) are the platform choosing where an investor's money goes, closer to a recommendation than a manual "Comprar" click on a specific offer — so the two riskier baskets require a valid, non-expired assessment matching or exceeding their risk tier. The safest basket (conservadora) never requires one, on the theory that an unknown risk tolerance is conservatively assumed to be fine with the safest option:

| Cesta | Perfil mínimo exigido |
|---|---|
| Conservadora (AA/A) | Nenhum |
| Diversificada (AA–C) | Moderado |
| Agressiva (B/C) | Arrojado |

Missing/expired → `403 suitability_required`; present but too conservative for the chosen basket → `403 suitability_mismatch` — the client surfaces both with a link straight to the questionnaire.

### Rebalanceamento sugerido de carteira (`lib/portfolioRebalance.ts`, Carteira & Histórico)

A free, deterministic recommendation engine — no LLM involved — that compares an investor's real current allocation against target bands for their suitability profile (reusing the conservador/moderado/arrojado profile above; defaults to a neutral "moderado" band, clearly labeled, if the investor hasn't completed the questionnaire) and flags two kinds of drift:

- **Rating drift** — actual % invested per rating (AA/A/B/C) vs. the profile's target band, only surfaced past a 10-point threshold so small rounding never generates noise.
- **Single-sacado concentration** — any one counterparty above a profile-scaled limit (15% conservador / 25% moderado / 35% arrojado), regardless of its rating.

Every suggestion names a concrete R$ amount to trim/add and never executes anything — same human-in-the-loop principle as the rest of the platform; the investor decides whether and how to act (e.g. listing an overweight position on the mercado secundário). `GET /historico/rebalanceamento`, surfaced as a card on Carteira & Histórico whenever the investor has at least one active position.

### Seguro com múltiplas seguradoras concorrendo (`lib/insuranceQuotes.ts`)

Every insurer used to quote the exact same flat `premioPct` for every duplicata regardless of risk — "compare seguradoras" in the UI was cosmetic, since the numbers never actually moved. Each of the 3 partner insurers now has its own deterministic, documented pricing formula driven by real attributes of the specific duplicata, so they genuinely disagree on price depending on the risk profile:

- **Too Seguros** ("Parceira desde 2024") specializes in low-risk paper — tightens its price as the sacado's score climbs, widens it for weaker scores.
- **Pottencial Seguradora** ("Maior cobertura de sinistro") prices flat regardless of score — its edge is coverage breadth, not risk selection — but adds a small surcharge on large tickets, since a single big claim concentrates more of its exposure.
- **Junto Seguros** ("Aprovação mais rápida") discounts duplicatas maturing soon (less time for something to go wrong before it pays out), holding its base rate otherwise.

The marketplace's "Contratar seguro" picker now shows 3 **live, per-offer** quotes, cheapest flagged as recommended, instead of one static catalog. The premium actually charged at contract time is what gets recorded (`insurance_settlements`) and is what the UI keeps showing afterward — a sacado's score moving later never retroactively changes what an investor is shown as having already paid.

### Relatório automático COAF/CVM (`lib/regulatoryReports.ts`)

What's real here is the actual document a compliance officer needs, correctly structured from real platform data, stopping exactly where a real government credential would be required — same honest-gap discipline as `docs/soc2-gap-assessment.md`:

- **Relatório COAF por caso** (admin **Compliance** → cada SAR aberto por `lib/suspiciousActivityMonitor.ts`) — gera um PDF no formato de uma Comunicação de Operação Suspeita real: identificação do comunicante e do envolvido (nome/CNPJ declarado no KYB), o indicador de ocorrência oficial mapeado do tipo de alerta (ex. `9.1` fracionamento), a descrição e a evidência real dos lançamentos analisados. `GET /admin/pld/suspeitas/:id/relatorio-coaf.pdf`.
- **Informe mensal CVM** (admin **Compliance**) — agrega dados reais do período (duplicatas emitidas, volume negociado no mercado primário e secundário, sinistros decididos, SARs abertos, base ativa de investidores/cedentes) em um PDF de apoio. `GET/admin/regulatorio/cvm-informe[.pdf]?period=YYYY-MM`.

### Central fiscal — informe de rendimentos (`lib/incomeTaxStatement.ts`)

Retorno em direitos creditórios is taxed for an investor the same way renda fixa is: IRRF pela tabela regressiva (Lei 11.033/2004) — 22,5% até 180 dias, 20% até 360, 17,5% até 720, 15% acima disso — calculada sobre o prazo entre a aplicação (compra) e o resgate (vencimento da duplicata). Lastro doesn't actually withhold anything today (settlement credits the full retorno), so this is a real, correctly-computed **estimate** for the investor's own IR declaration, not a live withholding engine and not a formal DIRF submission to Receita Federal (which needs Lastro's own e-CNPJ digital certificate and access to Receita's Sped/DIRF system — same honest-gap discipline as the COAF/CVM reports above). Every line is a real operation from the investor's own purchases; nothing projected. `GET /historico/informe-rendimentos[.pdf]?year=YYYY`, free for every investidor, surfaced as a card on Carteira & Histórico.

#### DARF — o outro lado da mesma obrigação (`lib/darfGenerator.ts`)

The informe above is the investor's side; this is the platform's: for IRRF-style renda-fixa withholding, it's the *fonte pagadora* (Lastro) who actually owes Receita Federal, not each investor individually. `buildDarfSummary(period)` aggregates the exact same IR regressive-table math (`aliquotaForDias`, reused directly from `lib/incomeTaxStatement.ts` — one bracket table, not two copies that could drift) across *every* investor's positions maturing in a given competência month, using a real, long-standing DARF código de receita (**3426** — IRRF sobre rendimentos de aplicações financeiras de renda fixa) and a commonly-used due-date rule (último dia útil do mês seguinte). Same honesty discipline as everywhere else this codebase touches tax/regulatory territory: it computes a real total from real data, but doesn't file or pay anything — Lastro doesn't actually withhold IR today, so this is "what Lastro would owe if it were withholding," clearly labeled as an estimate to confirm against current legislation, not a protocoled guia. `GET /admin/juridico/darf[.pdf]?period=YYYY-MM`, admin-only, card on Compliance → Regulatório next to the CVM informe.

`server/test/darf.test.ts` (5 tests): aggregates a real purchase's IR using the same bracket math as the investor-facing informe; zero for a period with no real maturities; admin-only route; real JSON + real PDF stream; malformed period falls back to the current month.

### Fundo de garantia / camada de proteção do marketplace (`lib/guaranteeFund.ts`)

A real pooled reserve for defaults on **uninsured** duplicatas — an insured one already has a real claims path via the seguradora (see "Seguro com múltiplas seguradoras concorrendo" above); this exists specifically for the gap that leaves open. Funded by 10% of Lastro's own platform fee on every primary purchase (`settlePurchase`), **never an extra charge** to cedente or investidor — just how Lastro allocates part of its own fee revenue (`guarantee_fund_ledger` table, migration `0036_guarantee_fund.sql`).

An investor sees every uninsured, genuinely-overdue position they hold with no open claim yet (`GET /guarantee-fund/eligible`) and can acionar the fund directly from Carteira & Histórico. An admin reviews each claim (`GET/POST /admin/guarantee-fund/claims[/:id/decidir]`); an approved payout is capped both by a coverage percentage (80% of the amount claimed — the fund never promises full recovery) **and** by the fund's real available balance (it can never pay out more than it actually has) — a real reserve, not an unlimited backstop pretending to be one. The fund's live balance is also part of the public Transparência page.

### Linha de crédito rotativa (`lib/creditLine.ts`)

A second, distinct lending product alongside duplicata purchase: working capital advanced against the **cedente's own real emission track record on Lastro** — not a specific receivable an investor is buying, capital from the platform itself. The limit is entirely derived and re-derived from the cedente's real last-90-days book (`computeCreditOffer`): needs at least 3 real duplicatas emitted in that window (no track record → not eligible, full stop), no open dispute involving any of the cedente's duplicatas (`listOpenDisputesByCedente` — an open dispute suspends the line until resolved), then `limite = (90-day emitted volume / 3) × a rating-based multiplier` (0.6/0.45/0.3/0.15 for AA/A/B/C — more conservative than the marketplace's own deságio bands, since this is unsecured against the cedente itself, not an insured/registered receivable), capped at R$3.000.000. Rate is also rating-based (2.2%–5.5% a.m.), locked in per draw so a later re-score never retroactively changes what's already owed.

Interest accrues lazily — same principle as the platform's other time-based computations (dynamic pricing's 30-day window, IR withholding bands): no cron job, whoever next reads the line (an overview call, a draw, a repayment) prorates whatever's actually owed since the last look and persists it. Draws credit the cedente's own extrato (`db/misc.ts`'s ledger) for real; repayments apply oldest-open-draw-first and debit it back. `GET/POST /credit-line[/draw|/repay]`, new "Linha de Crédito" nav item for cedentes (`pages/app/CreditLinePage.tsx`).

#### Funded by a real investor pool, not Lastro's own capital (`lib/creditLineFund.ts`)

Every draw above used to implicitly come from "Lastro's own money" with no source actually tracked. `lib/creditLineFund.ts` opens the line to real investor funding: a pool (`credit_line_fund_ledger`/`credit_line_fund_contributions`, migration `0039_credit_line_fund.sql`) that investors contribute real capital into, and that now has to have the money before a draw is allowed at all — `drawCreditLine` (in `lib/creditLine.ts`) checks the cedente's own limit *and* the pool's real balance, rejecting with `fund_insufficient` if the pool can't cover it even when the cedente is well within their own limit. Repayments (principal + interest) flow straight back into the pool per draw actually paid down, growing its real balance.

**Real per-investor yield attribution via a cota/NAV pricing model** (migration `0042_credit_line_fund_quotas.sql`) — closes what used to be a documented simplification: interest just grew the shared pool balance, benefiting "whoever held a position when it landed" rather than each contributor proportionally. Now every `aporte` buys quotas at the fund's current cota price (`getCotaPrice()` = NAV / total quotas outstanding, starting at R$1,00/cota at inception — the same bootstrap convention a real FIDC uses); every `resgate` sells quotas back at the current price. Interest returned from repayments never mints new quotas — it only grows NAV, so the price itself rises for whoever already holds quotas at that moment, the same mechanic a real FIDC cota uses to distribute yield proportional to how much/how long each investor actually had in the fund. NAV = real cash in the ledger + the real value of outstanding draws the pool currently owns (their last-accrued `saldo_devedor`, deliberately not re-accrued live to avoid a circular import with `lib/creditLine.ts` — the same lazy-accrual principle the rest of the platform already uses elsewhere, so the price can be very slightly stale for a draw nobody's looked at recently, never materially wrong). An investor can redeem up to `min(their quota-based equity value — principal plus accumulated yield, the pool's real available cash)`. `GET/POST /credit-line-fund[/contribuir|/resgatar]` now also returns `navFmt`/`cotaPriceFmt` (fund-wide) and `yourPositionFmt`/`yourPrincipalAportadoFmt` (equity vs. raw contributed principal, so an investor can see their yield); the "Linha de Crédito" page's pool card (`pages/app/CreditLinePage.tsx`'s `FundCard`) shows both.

`server/test/credit-line-fund.test.ts` (5 tests) + `server/test/credit-line.test.ts` extended (7 tests now, was 6): contribution grows the real pool balance and debits the investor's own ledger; non-investor rejected; redemption capped by real position/pool balance, rejects over-redeeming; a draw is rejected for real pool illiquidity even when comfortably within the cedente's own limit.

`server/test/credit-line-fund-quotas.test.ts` (2 tests): an early contributor's equity value grows beyond their raw contributed principal once a real draw is repaid with real (backdated, so the test doesn't depend on a live clock) accrued interest, while NAV grows without minting new quotas; a second investor contributing the exact same reais *after* the price has risen buys fewer quotas and ends up with a strictly smaller position than the earlier contributor — no windfall from yield that accrued before they had any money in; the fund overview exposes a real NAV and cota price.

`server/test/credit-line.test.ts` (7 tests): not eligible under 3 duplicatas/90d; eligible with a real non-zero limit/rate once there's a track record; suspended while a dispute is open; draw within limit succeeds and rejects one that exceeds it; repay settles a draw and reflects on the real ledger; repay-with-no-balance 404s and a non-positive draw/repay 400s; a draw is rejected for real pool illiquidity even when comfortably within the cedente's own limit.

### Fundo de garantia — teste de estresse Monte Carlo (`lib/guaranteeFundStressTest.ts`)

A real Monte Carlo simulation answering "how likely is today's actual fund balance to be exhausted by a bad quarter across today's actual uninsured book" — not the static coverage-percentage-vs-balance number the fund overview already shows. Builds the real current exposure (every active, uninsured, non-sandbox purchase — `db/duplicatas.ts`'s `listActiveUninsuredPurchases()`), assigns each position a default probability via `lib/defaultProbability.ts`'s `estimateDefaultProbability()` — the real trained ML model (`lib/mlScoring.ts`'s `predictDefaultProbability`) when one exists, or — the common case today, since the platform is too young to have enough labeled defaults — a documented **assumed** prior calibrated to typical Brazilian trade-receivables NPL ranges by rating (0.5%/1.5%/4%/9% for AA/A/B/C), labeled `pdSource: 'assumed'` everywhere it surfaces so it's never mistaken for measured history. That estimator is shared with `lib/agents/underwriting.ts`'s `prever_probabilidade_ml` tool, which used to just report "unavailable" whenever the ML model wasn't trained yet even though the exact same fallback prior already existed one file away — it now always answers, with a `fonte: 'ml' | 'assumida'` field so the underwriting agent (and its human reader) can tell which one produced the number. `server/test/default-probability.test.ts` (2 tests): falls back to the documented prior with no model trained; uses the real trained model once one exists.

Simulates thousands of scenarios using a single-factor Gaussian copula (the same structural idea behind the Vasicek model underlying Basel's IRB capital formula, simplified but real: one shared macro shock plus an idiosyncratic shock per position, blended by a correlation assumption) instead of treating defaults as independent coin flips, which would understate real tail risk. Reports P(fund depleted), expected loss, VaR 95%/99%, and expected shortfall beyond the balance. Deterministic and reproducible for a fixed seed (`mulberry32`), real `Math.random()` otherwise. `GET /admin/guarantee-fund/stress-test[?simulations=&correlation=]`, "Executar simulação" card on the admin Compliance tab.

### Tokenização/fracionamento de duplicatas grandes (`lib/fractionalOfferings.ts`)

### Postgres schema translation — validated against a real Postgres 16 (`scripts/postgres/`)

Upgrades `docs/postgres-migration.md`'s previously-theoretical "the data model is portable almost 1:1" into something actually run against a real server. `scripts/postgres/generate-schema.mjs` translates all 42 SQLite migrations to `server/src/db/migrations-postgres/*.sql`; `scripts/postgres/validate-schema.sh` applies every one of them, in order, to a real throwaway PostgreSQL 16 database via `psql` (`apt install postgresql-16` in this sandbox — genuinely installed and run, not simulated). All 42 apply cleanly and produce all 62 tables; a smoke test (insert a user, insert a duplicata referencing it, join them back) confirmed the foreign keys and constraints work correctly, not just parse.

The mechanical translation needed exactly two substitutions across all 42 files (`AUTOINCREMENT` → `GENERATED BY DEFAULT AS IDENTITY` — not `ALWAYS`, which the validation script's first real run rejected with `cannot insert a non-DEFAULT value into column "id"` since some migrations preserve original ids when rebuilding a table; and `datetime('now')` → `now()`). Two migrations (`0004`, `0006`) needed genuine hand-translation: both use SQLite's only way to widen a `CHECK` constraint (rebuild the whole table), and replaying that rebuild's `DROP TABLE users` against Postgres failed for a real reason — Postgres tracks foreign keys as catalog constraints and refuses to drop a table ten others still reference, where SQLite doesn't track FK dependents that way. The honest fix is that Postgres never needed the rebuild at all: `ALTER TABLE ... DROP/ADD CONSTRAINT` changes a CHECK directly. Full writeup of both real errors found and what the translation still doesn't cover (the runtime query layer's own `datetime`/`strftime` variants, the sync→async driver rewrite, per-test-file isolation) in `scripts/postgres/README.md` and the updated `docs/postgres-migration.md` — the driver/runtime-query-layer conversion remains real, unstarted work; only the schema is now verified. That verification now runs on every push/PR too, not just once by hand: CI's `postgres-schema-check` job (`.github/workflows/ci.yml`) re-translates and re-applies all 42 migrations against a real `postgres:16` service container, so a future migration that breaks Postgres portability gets caught automatically.

### Real stablecoin settlement rail (`lib/stablecoinRail.ts`)

A fourth deposit/withdraw method in **Conta & Liquidação**, alongside Pix, boleto and TED — aimed at two cases those three don't cover well: a non-resident (INR) investor funding a position without a manual SWIFT/câmbio step (see `lib/foreignInvestorCompliance.ts`), and settlement outside Pix/TED banking hours.

Modeled deliberately on the TED rail, not Pix/boleto: there is no BACEN-style standardized "confirm this cobrança" API for a stablecoin transfer, and a user self-attesting "I sent it" can't be trusted any more than a user self-attesting a TED landed — so there is no self-service "confirmar (simulado)" button. A real custodial/VASP provider (`STABLECOIN_PSP_*`) issues a dedicated deposit address and confirms via a real webhook (`POST /public/stablecoin-webhook`); without one, deposits fall back to Lastro's own static receiving wallet (`LASTRO_STABLECOIN_WALLET_ADDRESS`) with a reference an admin matches by hand against the real chain explorer (`GET /admin/stablecoin/pendentes`, `POST /admin/stablecoin/:referencia/confirmar`, optionally recording the tx hash). Neither configured = fully simulated wallet data, same as every other rail.

The regulatory point that matters more than the code: since Lei 14.478/2022 and the Banco Central's 2025 regulation of "prestadores de serviço de ativos virtuais" (VASPs), custodying or converting stablecoin on behalf of third parties is itself an authorized activity — `STABLECOIN_PSP_*` is meant to point at an already-licensed custodial/VASP partner's API, this repo can't make Lastro one just by setting an env var, the same reasoning `FOREIGN_INVESTOR_DISCLAIMER` already applies to the câmbio leg of a foreign offering.

`STABLECOIN_ASSET`/`STABLECOIN_NETWORK` (default `USDC`/`polygon`) are a platform-wide choice, not per-user. New tables: `stablecoin_deposits`, `stablecoin_payouts` (`0048_stablecoin_rail.sql`, mirrored in `migrations-postgres/`). New tests: `server/test/stablecoin-rail.test.ts` (9). Verified: `npm run typecheck`/`test` all green (server 96 files/546 tests, client 24/24, Node SDK 9/9).

Este é o primeiro PR de uma série de 4: cria o programa e a matrícula de cedentes elegíveis, sem ainda pular o leilão de fato (isso vem nos próximos PRs, depois que o fundo de fomento dedicado existir).

- **`confirming_programas`/`confirming_membros`** (migração `0061`) — um programa por sacado (`sacado_user_id UNIQUE`), com `rating`/`taxa_am` calculados uma vez na criação a partir da classificação de risco real do próprio sacado (`buildBlendedRiscoViewSync` + `estimateRateBand` — as mesmas funções que já precificam qualquer oferta no mercado aberto, nunca um número escolhido pelo sacado) e um `limite` que o sacado define, dentro de uma faixa (R$10 mil a R$5 milhões).
- **CNPJ autodeclarado uma vez** — reaproveita `UserSettings.companyCnpj` (até aqui só usado pelo AI CFO do cedente), agora também pelo sacado ao criar o programa.
- **Matrícula com base em histórico real**: `listarCedentesElegiveis` sugere cedentes que já têm aceites reais contra este sacado (`listAceitesBySacadoNome`, a mesma consulta que já resolve o Portal do Sacado) — não uma lista arbitrária.
- **`GET/POST /api/confirming/*`** — sacado cria/pausa/reativa o programa e matricula/remove cedentes; cedente só lê em quais programas está matriculado (`GET /minhas-matriculas`). Toda mutação grava evento de auditoria.
- **Client**: nova nav tab "Programa Confirming" pro sacado (nav dele tinha só 6 tabs — cabia folgado); do lado cedente, sem nova tab — um card "Meus Programas Confirming" dentro de Emitir Duplicata, o lugar mais natural pra ver a que sacados já tem acesso pré-aprovado.

Ainda não muda nada no fluxo de emissão/leilão em si — é só visão e configuração. Novos testes: `server/test/confirming.test.ts` (11 casos — criação com taxa real, limites de faixa, matrícula por histórico real, gating de papel, auditoria). Verificado: `npm run typecheck`/`build`/`test` todos verdes (server 102 arquivos/621 testes, client 24/24, sdks/node 9/9); `migrations-postgres/0061` conferido byte a byte contra `scripts/postgres/generate-schema.mjs`.

### Financiamento automático do Programa Confirming (3/4)

Terceira PR da série, a que de fato move dinheiro: emitir uma duplicata contra um sacado com programa ativo, sendo o cedente matriculado, agora pula o leilão inteiro — financiamento na hora, direto do fundo de fomento (PR 2).

- **`tentarFinanciarViaPrograma`** (`lib/confirmingCore.ts`) — chamado de dentro de `submitEmitir` (`lib/emitirCore.ts`) só **depois** que a duplicata está de fato aprovada (checklist 100%, não suspensa pelo Compliance AI Engine) e nunca em modo sandbox. Identifica o sacado pela mesma amarração de nome que o resto do app já usa (`getSacadoAccountByCompanyName` — igual ao aceite, igual à notificação de emissão), checa programa ativo + matrícula ativa + espaço no limite do programa e no sublimite do cedente (novo `confirming_membros.utilizado`, migração `0063`) antes de financiar.
- Quando financia: `createPurchase`/`settlePurchase` — os mesmos usados por uma compra manual no mercado aberto ou pelo auto-bid — na taxa do próprio programa, com capital da conta de sistema do Fundo de Fomento do Confirming (criada de forma preguiçosa na primeira compra, no mesmo padrão de conta-nunca-logável já usado por contas só-Google). A duplicata nunca passa por `'no_mercado'` — vai direto pra `'vendida'`.
- O aceite continua rodando sem nenhuma alteração — o financiamento não espera a confirmação do sacado (esse é o ponto do "confirming"); uma contestação posterior cai no fluxo de disputa que já existe pra qualquer duplicata comprada, sem código novo.
- **Limitação conhecida e documentada, não desta feature**: a plataforma como um todo ainda não modela um evento real de "recebimento no vencimento" pro caminho feliz (só existe pra recuperação via cobrança jurídica de atraso — `lib/legalCollectionFee.ts`). `fundoRetornoDePagamento` (PR 2) já existe pronta pra quando essa lacuna geral for fechada, mas não é o escopo desta PR resolvê-la.
- **Client**: tela de sucesso da emissão (`EmitirPage.tsx`) diferencia "financiada na hora pelo Programa Confirming" de "enviada ao Marketplace".

Novos testes: `server/test/confirming-auto-fund.test.ts` (6 casos — financiamento de ponta a ponta com o pool realmente debitado e o leilão genuinamente pulado, cedente não matriculado segue o fluxo normal, programa pausado nunca financia, limite do programa e sublimite do cedente respeitados, modo sandbox nunca financia). Verificado: `npm run typecheck`/`build`/`test` todos verdes (server 104 arquivos/635 testes, client 24/24, sdks/node 9/9); `migrations-postgres/0063` conferido byte a byte contra `scripts/postgres/generate-schema.mjs`.

### Monitoramento + ranking do Programa Confirming, e uma correção de segurança financeira

Segundo item da mesma auditoria: o Programa Confirming (série anterior) não tinha nenhum sinal de saúde/risco — taxa e limites ficavam congelados desde a criação, a lista de cedentes elegíveis era plana (sem ordenação, sem sinal de risco), e o admin não tinha como saber se os programas ativos estavam prometendo mais financiamento do que o fundo realmente tem em caixa.

- **Correção de bug** (`tentarFinanciarViaPrograma`, `lib/confirmingCore.ts`): o financiamento automático nunca checava `getFundoBalance()` antes de comprar — um programa com limite alto e pouco (ou nenhum) aporte real de investidor podia financiar do mesmo jeito, deixando o ledger do fundo negativo. Isso violava o mesmo princípio que já levou à remoção do fundo de garantia nesta sessão: a Lastro não carrega risco de capital próprio. Corrigido com um novo motivo de fallback `fundo_insuficiente` (mesmo padrão de `limite_programa_excedido`/`sublimite_excedido`), espelhando o precedente já existente em `drawCreditLine` (`lib/creditLine.ts`), que já checava `getFundBalance()` antes de liberar um saque.
- **`listarCedentesElegiveis`** agora ordena por volume histórico decrescente e traz duas informações novas por cedente: `sublimiteSugeridoFmt` (a própria média do que esse cedente já emitiu contra este sacado — não um número inventado) e `disputasAbertas` (via `listOpenDisputesByCedente`, o mesmo sinal que já gate a linha de crédito rotativa), pro sacado ver risco antes de matricular alguém, não só volume.
- **`listProgramasParaAdmin`** ganhou `utilizacaoPct`/`alertaLimite` (≥ 80% do limite acende um aviso), e uma nova **`buildConfirmingHealthSummary`** compara quanto os programas ativos prometem financiar (`limite - utilizado`, uma promessa do sacado) contra o caixa real do fundo (`fundoSuficiente`) — o mesmo saldo que `tentarFinanciarViaPrograma` agora checa antes de financiar.
- **Client**: `ConfirmingPage.tsx` mostra a sugestão de sublimite e um badge de disputas em aberto por fornecedor elegível; `ConfirmingAdminPanel.tsx` mostra um banner vermelho quando o fundo não tem caixa suficiente pra cobrir a promessa dos programas ativos, e um badge âmbar de utilização por programa perto do limite.

### Pagamento no vencimento — a plataforma inteira nunca modelava esse evento

Investigação disparada pelo achado original ("o fundo do Confirming nunca recebe capital de volta", `lib/confirmingFundo.ts`'s `fundoRetornoDePagamento` sem chamador em produção) revelou um escopo maior: **nenhuma parte da plataforma modelava "o sacado pagou a duplicata no vencimento, caminho feliz"** — nem o marketplace normal, nem a linha de crédito, nem o Confirming. O único jeito de uma duplicata virar `'paga'` era via `recordRecovery()` (cobrança jurídica por atraso, disparada pelo admin), e mesmo esse fluxo nunca creditava o principal de volta ao credor — só debitava a fee da Lastro.

- **`lib/settlement.ts`**: nova `settleAtMaturity` — credita o credor atual (`currentCreditorFor`, já existente em `lib/legalCollectionFee.ts`) pelo valor de face cheio; a taxa de plataforma já foi cobrada na compra, nada é descontado de novo aqui.
- **`lib/aceiteCore.ts`**: novo self-report do sacado (`reportPayment`, `POST /aceites/:id/pagamento`) — mesmo padrão de auto-serviço que `lib/creditLine.ts`'s `repayCreditLine` já usa (o pagador reporta, sem webhook de banco real disponível hoje). Elegível enquanto a duplicata for uma posição viva (`aprovada`/`vendida`) sem disputa em aberto; marca a duplicata `'paga'`, confirma o aceite se ainda estava `'aguardando'` (pagar implica aceitar), e — se o credor for a conta de sistema do Programa Confirming — também chama `fundoRetornoDePagamento`, fechando a lacuna original.
- **`lib/confirmingFundo.ts`**: `computeFundoNav()` agora soma as posições em aberto do fundo (`sumOutstandingPurchasesByInvestor`, nova em `db/duplicatas.ts`) além do caixa — mesmo espírito de `creditLineFund.ts`'s `computeFundNav`; só caixa subestimava o NAV real enquanto o fundo tinha financiamentos ainda não pagos.
- **`SacadoPage.tsx`**: botão "Reportar pagamento" por duplicata elegível, ao lado dos botões de confirmar/contestar já existentes.

Novos testes: `server/test/duplicata-payment.test.ts` — os 3 caminhos de credor (investidor via compra no marketplace, cedente quando a duplicata nunca foi vendida, fundo do Confirming com `getFundoBalance()`/`computeFundoNav()` conferidos antes/depois) e os bloqueios (papel diferente de sacado, duplicata de outra empresa, disputa em aberto, idempotência). Verificado: `npm run typecheck`/`build`/`test` todos verdes (server 109 arquivos/659 testes, client 24/24, sdks/node 9/9).

### O investidor pagava o valor de face cheio e recebia o valor de face cheio de volta — zero retorno real

Achado numa simulação real de ponta a ponta (R$50.000, emissão → leilão → compra → aceite → pagamento no vencimento): com o pagamento no vencimento já funcionando (achado acima), o investidor fechava a operação com saldo líquido **zero** — pagou R$50.000 pela duplicata, recebeu R$50.000 de volta. O "deságio" mostrado em todo canto da UI (marketplace, leilão, cestas, Confirming) nunca foi de fato descontado de nenhuma movimentação real de dinheiro: `lib/settlement.ts`'s `settlePurchase` sempre cobrou o investidor pelo valor de face inteiro, não pelo preço com deságio. Só a taxa de plataforma (cobrada do cedente) era um número real; o retorno do investidor — a razão de existir de financiar antecipadamente — nunca existiu.

- **`lib/marketCompute.ts`**: nova `computePurchasePrice(d, rateOverridePct?)` — preço real de compra (`precoCompra = valor - valor × taxa a.m. × prazoDias/30`, mesma fórmula que o simulador público do Comparador de Taxas já usa para a estimativa, agora também aplicada de verdade), com um teto de 60% de deságio pra nunca precificar a quase zero um papel muito longo ou de taxa muito alta. `effectiveMonthlyRatePct` extraída da lógica que já existia em `buildOfferView` (taxa real do book — `dynamicPricing.ts` — ou a taxa já negociada, ex. `programa.taxa_am` do Confirming). O feed do marketplace agora expõe `precoCompra`/`precoCompraFmt` — o cliente mostra "Você paga R$X" ao lado do valor de face.
- **`lib/settlement.ts`**: `settlePurchase` passa a receber `precoCompra` explicitamente — débito do investidor e crédito líquido do cedente usam o preço com deságio; a taxa de plataforma continua calculada sobre o valor de face (tamanho do recebível, não do que foi pago por ele).

### `purchases.valor` ambíguo: "Investido" e retorno % usavam valor de face, não o preço pago real

Fechando o terceiro achado em aberto da PR #55. `purchases.valor` guarda valor de face numa compra primária/cesta/Confirming (`market.ts`, `cestasCore.ts`, `confirmingCore.ts` sempre chamam `createPurchase` com `duplicata.valor`) mas preço pago numa compra originada de revenda (`resaleCore.ts` passa o preço da revenda) — só que `purchases.retorno` já é, de forma universal e comprovada desde a correção do retorno fabricado, `valor de face − preço pago`. Ou seja: **preço pago real = valor de face (`duplicatas.valor`) − retorno**, sempre, enquanto a posição não foi revendida — sem precisar de coluna nova.

Isso expunha dois bugs reais, não só o `discountRatio` já documentado:
- **`routes/historico.ts`, `lib/institutionalReporting.ts`, `lib/portfolioRebalance.ts`, `lib/investorPerformance.ts`** somavam/dividiam por `purchases.valor` direto — pra uma compra primária (a maioria), isso é valor de face, não o dinheiro que de fato saiu do bolso do investidor. `totalInvestido`/"Investido" ficavam superestimados, e toda métrica derivada (`rentMedia`, `retornoAnualizadoPct`, `retornoMedioPonderadoPct`, `volatilidadePct`, `sharpeLike` do dashboard de performance institucional) saía sistematicamente subestimada.
- **`db/resaleListings.ts`'s `listActiveListings`** juntava `original_valor` com `purchases.valor` em vez de `duplicatas.valor` — pra um anúncio originado de uma revenda anterior, isso comparava contra um preço de revenda anterior em vez do valor de face real, afetando tanto a exibição (`variacaoPct` no mercado secundário) quanto a ORDEM real de execução de um block trade sweep (`discountRatio`, `lib/blockTrade.ts`).

**Cuidado importante na correção**: a identidade `preço pago = valor de face − retorno` só vale enquanto a posição nunca foi revendida — `deactivatePurchase` (`db/resaleListings.ts`) sobrescreve `retorno` com o ganho/perda REALIZADO da revenda assim que a posição é fechada, quebrando essa relação. Pra uma posição já revendida (`active = 0`), "Investido" continua vindo de `purchases.valor` direto (nunca tocado por `deactivatePurchase`) — o registro histórico correto de quanto foi investido pra abrir aquela posição encerrada — em vez de recalcular por cima de um `retorno` que já significa outra coisa.

- **`db/duplicatas.ts`'s `listPurchasesByInvestor`**: passou a selecionar `d.valor as faceValor` (join com `duplicatas` que já existia).
- **`db/resaleListings.ts`'s `listActiveListings`**: `original_valor` agora vem de `d.valor` (valor de face real), não de `purchases.valor`.
- Nos 4 arquivos afetados: `precoPago(p) = p.active ? p.faceValor - p.retorno : p.valor`.

Novo `server/test/purchases-valor-preco-pago.test.ts`: `totalInvestidoFmt` do relatório institucional e do rebalanceamento batem com o preço pago real, não o valor de face; `retornoAnualizadoPct` do dashboard de performance sai maior que a versão ingênua (dividida por valor de face); uma posição já revendida mantém "Investido" como o registro original; `discountRatio` do block trade escolhe corretamente o anúncio com maior desconto real vs. valor de face, mesmo quando ele vem de uma revenda anterior com um preço-base diferente. `server/test/settlement.test.ts`/`investor-performance.test.ts` atualizados (assumiam valor de face como "Investido" — exatamente o bug). Verificado: `npm run typecheck`/`build`/`test` todos verdes (server 116 arquivos/710 testes).

### Fundo de Fomento do Confirming passa a disputar dentro do leilão — nunca mais um atalho pro próprio fundo

O campo `financiadoViaPrograma` (resposta de `submitEmitir`, sempre `false` desde a mudança de gate acima nesse instante) saiu da API interna e da tela de sucesso da emissão (`EmitirPage.tsx`) — não é usado por `routes/v1.ts` (API pública) nem pelos SDKs.

Sem vantagem estrutural: se um humano ou outro bot for mais rápido, ganha ele.

### Automação de Lances: escada de taxa por classe de rating (substitui o teto fixo) + faixa mesclada nas cestas

Pedido do usuário: a Automação de Lances tinha um único campo, "Taxa máxima a oferecer" (`autoBidRules.taxaMax`) — na prática um teto de risco (`offerRate <= taxaMax`), não uma proposta de negociação real (o preço sempre foi calculado pelo servidor, `computePurchasePrice(d)`, sem nenhum override vindo do investidor — confirmado em `routes/market.ts`, `maybeTick` e `lib/agents/autoBid.ts`). O pedido: configurar, **por classe de rating (AA/A/B/C)**, onde a automação começa exigente (o melhor deságio da classe) e o quanto relaxa a cada etapa até uma meta/piso mínimo aceitável — e, ao montar uma cesta que mistura classes, mostrar a faixa média mesclando-as.

- **`UserSettings.autoBidLadder`** (`db/types.ts`) — um `LadderConfig` por rating (`taxaInicial`/`taxaAlvo` nulos por padrão, `decrementoPorEtapa: 0.1`, `intervaloHoras: 4`). `taxaMax` saiu de `autoBidRules` — era vestigial.
- **`lib/autoBidLadder.ts`** (novo) — funções puras: `currentFloor` (o piso que a automação aceita agora — começa em `taxaInicial ?? estimateRateBand(rating).max` e decai `decrementoPorEtapa` a cada `intervaloHoras` sem compra, nunca abaixo de `taxaAlvo ?? estimateRateBand(rating).min` — a banda ao vivo, ajustada por liquidez real, é o default sem duplicar número nenhum), `nextStepAt`, `armLadder`.
- **`routes/automation.ts`**: `passesTaxa` inverte de teto (`offerRate <= taxaMax`) pra piso decrescente (`offerRate >= currentFloor(...)`). Uma compra bem-sucedida **rearma** a escada da classe comprada (o próximo ciclo volta a ser exigente); ligar a automação rearma toda classe com alocação > 0 na diversificação. Nova rota `POST /automacao/ladder` (`{rating, field, value}`, mesmo padrão de `/rule`/`/diversification`) — recusa taxa inicial menor que a taxa alvo (a escada só desce) e decremento/intervalo ≤ 0.
- **Cestas** (`lib/cestasCore.ts`'s `buildCestaRange`, exposto em `GET /cestas`): faixa de deságio mesclando automaticamente as classes que a cesta aceita — olha as ofertas de todas elas juntas (peso real = quanto tem aberto agora em cada uma, não um peso arbitrário por classe). Real quando há oferta compra´vel; cai pra banda teórica (`estimateRateBand` por classe) quando a cesta está vazia — mesmo espírito de "simulado quando não há dado real" já usado no resto do código.
- **Client**: `AutomacaoPage.tsx` troca o campo único por um card "Escada de lances por classe de rating" (uma linha por classe com alocação > 0, 4 campos + piso atual e próxima queda); `CestasPage.tsx` mostra "Faixa hoje"/"Faixa teórica" por cesta.

Novo `server/test/automation-ladder.test.ts` (15 casos — decaimento por etapa, nunca abaixo do alvo, banda ao vivo como default, validação da rota, rearme após compra numa duplicata criada direto pro teste). `automation-routes.test.ts`/`comparador-dashboard-cestas.test.ts` ajustados pro novo formato. Verificado: `npm run typecheck`/`build`/`test` todos verdes (server 747 testes, client 26/26, sdks/node 9/9).

### Acessibilidade: tabelas com semântica e rótulo em todo campo de formulário

Última frente da revisão de interface. Antes disto, um leitor de tela não anunciava cabeçalho
de coluna nas tabelas nem dizia do que era cada campo de formulário.

**Dois números do diagnóstico inicial estavam errados** e a medição real corrigiu:

| | Diagnóstico inicial | Real |
|---|---|---|
| Tabelas | "95 grids de div" | **6 tabelas de dados** — os outros 89 grids são layout (cards de preço, KPIs, seções da landing) |
| Campos sem rótulo | "~37 inputs" | **111 controles**, dos quais **79 não tinham nem rótulo nem placeholder** |

Os 79 eram o caso grave: o leitor anunciava só "caixa de edição", sem dizer do quê. Entre eles,
o `<select>` de categoria em Contas a Pagar, o campo de data de vencimento, as credenciais de
SAP/TOTVS/Omie e o campo de senha que confirma a **exclusão da conta** em Perfil.

**`components/ui/Table.tsx`** (novo): `Table`/`TableHead`/`TableRow` existiam dentro de
`Modal.tsx` (colocação estranha) com **zero usos** — código morto desde sempre, enquanto as 6
tabelas repetiam a mesma marcação à mão. Saíram do limbo, ganharam `TableBody`/`TableCell` e os
papéis ARIA.

*Decisão técnica que muda o que eu havia recomendado no diagnóstico*: eu tinha proposto
"tabelas semânticas (`<table>`)". Pesquisando o terreno, isso sairia **pior**. As colunas são
dimensionadas com `gridTemplateColumns` fracionário (`1.3fr 0.9fr 0.8fr…`), sem equivalente
direto em layout de tabela; preservar o visual exigiria `display: grid` na `<table>` com
`display: contents` nas linhas — e `display: contents` **remove** justamente a semântica de
tabela em vários leitores de tela, anulando o ganho. A alternativa seria reconstruir o layout
das 6, arriscando regressão. Os papéis ARIA (`table`/`rowgroup`/`row`/`columnheader`/`cell`)
são a solução padrão quando o layout exige CSS Grid: o leitor anuncia "tabela", navega por
células e lê o cabeçalho junto com o valor ("Vencimento: 22/09/2026"), com risco visual zero.

**Rótulos**: os 32 controles que tinham placeholder ganharam `aria-label` com o mesmo texto
(placeholder não é rótulo — some ao digitar e nem sempre é anunciado). Os 79 sem dica nenhuma
receberam `aria-label` escrito caso a caso a partir do que o campo realmente faz

## Running with Docker

```bash
docker compose up --build
```

Builds the client and server, then serves everything (API + static SPA + SPA fallback routing) from a single container on `http://localhost:4000`. Data and uploads persist in named volumes across restarts. Redis is included for the optional WebSocket relay but isn't required for a single instance. This is the quick-start path — no HTTPS, insecure default `JWT_SECRET`, meant for local use.

### Production deploy

For a real internet-facing deployment (real domain, automatic HTTPS, hardened container, required secrets instead of insecure defaults), use `docker-compose.prod.yml` + the bundled `Caddyfile` instead — see **[`DEPLOY.md`](DEPLOY.md)** for the full step-by-step runbook (DNS, `.env` secrets, first boot, creating the first real admin account, backups). docker compose -f docker-compose.prod.yml up -d --build

## Roles

Role is chosen once at registration (or via a demo account) and is fixed to that account/company:

- **Investidor/Financiador** — Dashboard, Marketplace, Automação de Lances (Pro+), Análise de Risco, Carteira & Histórico, Comparador de Taxas, Compliance, Conta & Liquidação, Modelo de Receita, Assinatura, Disputas, Perfil
- **Empresa (cedente)** — Dashboard, Integrações ERP, Emitir Duplicata (5/mês no Básico), Minhas Duplicatas, Aceite do Sacado (read-only), Análise de Risco, Carteira & Histórico, Compliance, Desenvolvedores (Empresarial), Conta & Liquidação, Modelo de Receita, Assinatura, Disputas, Perfil
- **Empresa (sacado)** — Dashboard, Portal do Sacado (confirmar/contestar), Carteira & Histórico, Conta & Liquidação, Disputas, Perfil
- **Admin (back-office)** — fila de aprovação de KYB, arbitragem de disputas, trilha de auditoria; não é uma role auto-cadastrável. Em desenvolvimento existe via o seed padrão (`admin@lastro.demo`); em produção (`NODE_ENV=production`) esse seed é pulado por padrão e a primeira conta admin real é criada com `npm run create-admin --workspace=server` (ver [`DEPLOY.md`](DEPLOY.md)).
- **Seguradora parceira** — Painel da Seguradora (apólices e sinistros), Perfil. Auto-cadastrável, escolhendo qual das três seguradoras parceiras a conta representa.
- **Auditor (somente leitura)** — Painel de Auditoria (trilha de auditoria, compliance, reconciliação, PLD), Perfil. Não é auto-cadastrável (mesma razão do admin — ver `lib/createAuditorAccount.ts`); só pode ser criado por um admin já autenticado (back-office → aba **Auditoria** → **Contas de auditoria**). Zero rotas de escrita em todo o papel.

A new investidor account is routed through a 3-step KYB (institutional credentialing) modal, including a real document upload, before entering the platform; submitting it puts the account in `pending` status (visible in the platform in read-only "modo consulta" per the design copy) until an admin approves or rejects it from the back-office. A sacado can only see and act on duplicatas whose `sacado_nome` matches their own company name — the cedente sees the same aceites read-only, since only the actual sacado can legally confirm or contest a debt.

## Known gaps / things a real deployment would still need

These require external commercial contracts or infrastructure this environment can't provide, so they're deliberately left as clearly-marked simulations rather than half-built integrations:

- **CERC/B3/Núclea/Grafeno registry integration is real-when-configured, not verified against their actual contracts** — `lib/registradoras.ts` makes a real HTTP call per the shape described above when `REGISTRADORA_*_API_URL/KEY` is set (falling back to a locally-generated registro number otherwise), and `POST /compliance/dup-check` additionally queries the configured registradora's own duplicidade-check endpoint per match. What's still missing is a *verified* copy of any one registradora's real private API contract — get that from an actual integration agreement and this adapter is the place to adjust it.
- **Real credit bureau score is real-when-configured** — `lib/creditBureau.ts` blends in a live Serasa/Boa Vista/Quod score when `BUREAU_API_URL/KEY` is set; without it, the risk score stays internal + network-signal only (no bureau data blended in).
- **Real payment rails are real-when-configured** — `lib/paymentRail.ts` (Pix), `lib/boletoRail.ts` (boleto), `lib/tedRail.ts` (TED) and `lib/stablecoinRail.ts` (USDC/USDT/BRLA...) all implement real, standard-shaped contracts; you still need a real PSP/banking/custodial contract for money to actually move. Pix is the dominant instant-transfer rail in Brazil and was prioritized first; boleto and TED followed to cover receivables collection and large institutional transfers respectively; stablecoin is the odd one out regulatorily, not just technically — see "Real stablecoin settlement rail" above for why `STABLECOIN_PSP_*` must point at an already Banco-Central-authorized VASP, unlike the other three where the licensed party is a conventional PSP/bank.
- **PLD/FT (AML) screening is real-when-configured, and only partially covers Brazilian compliance sources even then** — `SANCTIONS_LIVE_FEED=true` checks the real, free OFAC SDN list; `PLD_PROVIDER_API_URL/KEY` plugs in a paid provider ahead of it. Neither is a live COAF/CVM feed specifically, and the fictitious `sanctions_watchlist_demo` table is still the final fallback when neither is configured. There's also no automated suspicious-transaction monitoring beyond the emission-time value-anomaly and NF-e-reuse alerts already computed in `lib/fraudDetection.ts`, and no COAF reporting channel.
- **ERP integration is real for Omie, SAP and TOTVS** — `lib/erpConnectors/omie.ts`, `sap.ts` and `totvs.ts` are all genuine, immediately-usable integrations: any cedente's own Omie/SAP Business One/TOTVS account works with their own credentials, no Lastro-side contract needed, validated against each provider's real API contract, and can prefill Emitir Duplicata or feed the opt-in auto-emissão job.
- **WhatsApp/SMS is real-when-configured** — `lib/smsNotifier.ts` sends via Twilio's real API when `TWILIO_*` is set (opt-in per user in Perfil); unconfigured, messages are logged instead of sent, same as email without `SMTP_HOST`.
- **Contract-reading AI is now real, when `ANTHROPIC_API_KEY` is set** — see "Claude-assisted features" above (`lib/contractAnalysis.ts`). Unconfigured, it still falls back to the original static sample copy, clearly marked "Simulado" in the UI.
- **Registradoras (CERC/B3/Núclea) are not a login role** — that's a deliberate design choice, not a gap: registries are infrastructure Lastro integrates *with*, not accounts that log into Lastro. Banks/FIDCs/securitizadoras/factorings are represented as sub-types of the `investidor` role (the `tipo de instituição` field on KYB) rather than as separate roles, since they all use the exact same buy/fund workflow — only seguradora warranted its own role, because its dashboard and actions (apólices, sinistros) are genuinely different from every other role's.
- **Sandbox (`lastro_test_…`) keys now have real, isolated data** — closed in the "o que podemos melhorar" pass (`lib/sandboxData.ts`, `db/duplicatas.ts`): duplicatas created via a test-mode key are tagged `sandbox=1` and filtered out of every live/internal read (Minhas Duplicatas, Marketplace, Portal do Sacado, monthly emit-limit counting) at the query layer, and a test-mode `/v1/duplicatas/:id` lookup 404s on a live ID (and vice versa). Generating a test key auto-seeds a small deterministic demo dataset so a partner has something to `GET` immediately. Sandbox emissions never hit a real registradora regardless of configuration. Extended to aceites and disputes in the "o que está faltando" pass, and to insurance sinistro claims (`GET/POST /v1/seguradora[/sinistro/:id/decidir]`, `db/duplicatas.ts`'s `listInsuredByInsurerKey`/`listClaimableByInsurerKey` — previously hardcoded to the live plane regardless of caller, a real isolation gap for a partner-facing claim-decision endpoint) since — same pattern as aceites: a test-mode seguradora key only ever sees/decides its own sandbox sinistros, a live key can't even resolve a sandbox sinistro's ID to act on it, and vice versa.
- **SQLite as the datastore** — works well for this scale, but would need a move to Postgres for real multi-instance horizontal scaling (team invites, 2FA and multi-seat accounts are already real — see "Platform hardening" above).
- **Enterprise SSO/SAML is now real-when-configured** (see "Enterprise SSO/SAML" above) — an earlier pass in this project judged this out of scope on the theory that "no live IdP to test against in this sandbox" meant it couldn't be honestly built at all. On reflection that conflated two different things: every other real-when-configured integration in this codebase (Stripe, the credit bureau, the registradoras) has the exact same "no live counterparty reachable from this sandbox" limitation and is still legitimately implemented and trusted to work against the real thing once configured. SAML turned out to be no different — `lib/samlSso.ts` performs real signature verification via `samlify`, not a mock. What's genuinely still missing is a smoke test against one specific real IdP (Okta/Azure AD/etc.), which no environment available here can provide.
- **Cashflow forecast's slower-payment/unplanned-expense scenario shocks are stated assumptions, not fitted models** — see "AI CFO, Contas a Pagar, Reconciliation Agent, funding explainability" above; same honesty `PD_MULTIPLIER` already carried, now extended to `RECEIVABLE_DELAY_DAYS`/`UNPLANNED_EXPENSE_PCT_OF_PAYABLES`. Funding explainability's liquidity signal is segmented by rating but not also by tenor bucket. Contas a Pagar's ERP sync (see "Contas a Pagar via ERP" above) is closed for Omie (real, documented API); the SAP/TOTVS equivalents follow the exact same honesty the pre-existing contas-a-receber connectors already carried — real request shape, not yet verified against a live tenant of either.
